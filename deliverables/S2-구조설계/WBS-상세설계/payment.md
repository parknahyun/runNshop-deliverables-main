# WBS (계획·실적 통합) — Payment 도메인 (Bolt 기준)

> **단계**: 구조설계 (S2) Task 산출물, Scope: Domain→Bolt
> **문서종류**: Task (계획+실적을 같은 표에 유지하는 living document — 작업 끝날 때마다 갱신)
>
> **작성 목적**: Payment 도메인이 소유하는 작업 항목을 [order.md](order.md)의 **Bolt1~Bolt16**(매트릭스 열) 기준으로 관리한다. Bolt 구성·산정·상태는 order.md가 원본이고, 이 문서는 그 중 Payment 소유 작업 항목의 원본(소유 도메인 WBS)이다 — 작업 항목은 도메인 1개 안에서 완결된다(방법론 부록 A 기준 2). Payment 작업이 가장 많이 들어가는 Bolt는 **Bolt5 주문 결제**(PG 연동·카드·간편결제)와 **Bolt10 클레임 결제**(수단별 환불)다.
>
> **결제수단 모듈별 처리**: 결제수단(카드·가상계좌·간편결제·계좌이체·포인트/복합)을 모듈 단위로 구현한다. 모듈 구조(안): `PaymentService`(오케스트레이션) → `PaymentMethodModule`(수단별) → `PgRouter` → `PgGateway`(포트, Mock·실 PG 어댑터).
> **확장 원칙(모듈 개발만으로 확장)**: 새 PG나 결제수단은 **모듈(어댑터) 추가만으로** 끝나야 한다. 코어(SPI·레지스트리·라우터·웹훅 라우터·상태 정규화·계약 테스트 킷)는 한 번 만들고, PG는 `PgGateway` 구현 모듈, 결제수단은 `PaymentMethodModule` 구현 모듈로 추가한다(Spring 빈 자동 등록, 수단·PG 설정은 DB 카탈로그·라우팅 테이블). 모듈은 공통 계약 테스트 킷을 통과해야 하고, 추가 시 수정 범위는 `payment` 모듈 패키지와 설정 데이터로 한정한다.
> **인증·승인 분리(카드)**: 카드 결제는 **채널별 인증**(PC 웹·모바일 웹·앱 — PG별로 방식이 다름)과 **PG별 승인**을 분리한다. PG 모듈은 (채널별 인증 어댑터, 승인, 취소·환불, 조회, 웹훅)을 한 묶음으로 추가하고, 클라이언트는 서버가 내려주는 인증 요청 기술(`AuthDescriptor`: POPUP/REDIRECT/APP_SCHEME/SDK + URL·파라미터)을 채널별 공통 결제창 런처로 처리하므로 PG 추가 시 클라이언트 수정이 없다. 채널은 요청 헤더로 전달(`PC_WEB`/`MOBILE_WEB`/`APP`).
> **주문·클레임 영향 0**: Order·Claim은 안정된 `PaymentApi`(결제요청·환불·조회·사용 가능 수단 조회, 수단·PG에 무관한 정규화된 결과)만 사용하고 수단 코드·PG 코드를 하드코딩하지 않는다(현재 위반: `OrderService.validatePayRequest()`의 수단 허용 목록·카드 차단, `PaymentService`의 가상계좌 분기·라벨 맵, FE `OrderBottomBar`의 카드 차단 — SC03 'Order·Claim 결제 의존 격리' Bolt에서 제거). 클레임 환불·배송비 결제도 같은 `PaymentApi`를 쓴다. 검증: 모듈 추가 PR이 `order`·`claim` 패키지를 건드리지 않고, 기존 Order·Claim 회귀 시나리오가 그대로 통과해야 한다.
> **Bolt 절차·산정 모델**: [order.md](order.md) 머리말과 동일(9단계, AI 0.5h·휴먼 1.0h 최소, 6·7은 휴먼 2단계, 반복·보정 최소 2회). 휴먼 시간은 Bolt 단위로 통합 산정하므로 이 표는 항목별 AI 시간을 보인다.
