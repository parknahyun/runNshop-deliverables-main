## 0. 정책 개요

### 0.1 목적

상품(Catalog)의 등록부터 전시, 상품 리뷰까지 — Catalog 도메인이 책임지는 세 업무영역
(상품관리·전시관리·상품리뷰관리)에 필요한 공통 정책을 정의하여, 판매자(벤더)와 직매입 상품이
일관된 기준에 따라 등록·관리·노출·평가되고 플랫폼 운영 규칙이 명확하게 적용되도록 한다.

- 상품 등록·심사·상태 전이·가격·수수료 기준 정의 (상품관리)
- 상품 노출·정렬·전시 구성·기획전 운영 기준 정의 (전시관리)
- 상품 리뷰 작성·평점·보상·검수·신고 운영 기준 정의 (상품리뷰관리)
- 다른 도메인(Order·Promotion·Member·Community)과의 연동 경계 정의

### 0.2 적용 범위

본 정책은 상품의 등록부터 심사·판매·전시·리뷰까지 Catalog 도메인이 직접 책임지는 범위를
대상으로 한다.

**포함 범위**

- 상품 등록(직매입/입점형)·심사·반려·재고연동·가격·수수료 정책 (Part I. 상품관리)
- 노출 우선순위·전시 구조·기획전·홈 화면·프로모션 전시연계 정책 (Part II. 전시관리)
- 상품 리뷰 작성·평점·보상·검수·신고·판매자 응대 정책 (Part III. 상품리뷰관리)
- 판매자 단위 배송 정책 (Order 연동 경계)
- 화면별 할인가 노출 정책 (Promotion 연동 경계, Order DBA §2.5 역참조 수신)
- 연관상품 추천 위젯 정책 (Order DBA §2.11 역참조 수신)



### 0.3 용어 정의

| 용어 | 정의 |
|---|---|
| 상품 | 판매자 또는 플랫폼이 판매 목적으로 등록하는 재화 단위(Product) — 마스터 성격 속성(이름·카테고리·정가·공급가) |
| 직매입 | 플랫폼(자사)이 직접 매입·등록하는 상품. 심사 게이트 없이 등록 즉시 판매 가능(ON_SALE) |
| 입점형 | 판매자가 등록하는 상품. 심사요청 → MD 심사 → 승인/반려 절차를 거침 |
| 심사 | MD가 입점형 상품의 판매 가능 여부를 검토·판정하는 절차 |
| 정가 | 소비자 기준 공식 가격, 할인 적용 전 표시 기준(`price_original`) |
| 판매가 | 실제 결제 기준 가격(`price_sale`). `cat_product`의 컬럼이 아니며 저장하지 않는다 — 조회 시점에 정가와 할인 정보(§1.7.2)로 계산하는 값이다 |
| 판매자 공급가 | 정산 계산 기준 가격, 고객에게 노출하지 않음(`price_supply`) |
| SKU | 옵션(색상·사이즈 등) 조합별 재고·가격 관리 최소 단위 |
| 출시일 | `release_date` — 판매자·MD가 상품 등록 시 입력하는 선택 입력 항목. 입력하지 않으면 등록일시가 자동 입력되어 NULL로 저장되지 않는다. 검색 정렬 기준이자 노출 게이트 기준 |
| 노출 우선순위 | 상품 목록에서 상품이 보이는 순서를 결정하는 규칙(MD 수동 설정 또는 AI 추천 점수) |
| 전시 페이지 | 기획전·이벤트 등을 노출하기 위해 구성하는 페이지 단위 콘텐츠(`cat_display_page`, Catalog 소유) |
| 기획전 | Promotion이 소유하는 프로모션 이벤트 단위(`prm_exhibition`) — Catalog의 "전시 페이지"와는 다른 엔티티 |
| 표준 카테고리 | 상품 분류체계(§1.2) — 대분류-중분류-소분류 3단계, 상품이 귀속되는 분류(소분류 1개) |
| 전시 카테고리 | 고객 화면에 노출되는 메뉴·카테고리 그리드 분류(§2.5) — 표준 카테고리와 별도 엔티티, 대분류/중분류/소분류 3단계 트리, 상품은 소분류에만 매핑 |
| 판매자 단위 배송 | 배송비·묶음배송 처리를 상품이 아닌 판매자(벤더) 단위로 묶는 원칙 |
| 리뷰 | 구매확정한 회원이 상품에 대해 작성하는 평가 콘텐츠(텍스트/포토/동영상) |
| 평점 | 리뷰에 부여하는 정량 점수. 상품 단위로 평균 집계 |
| 태그 | 판매자가 자유 입력하는 검색 키워드(§1.3.4) — 카테고리를 대신해 세분화된 검색·필터링을 담당 |

|---|---|---|

| ⑦ | 업무영역 분리 | 상품관리(판매 가능 여부)·전시관리(노출 여부)·상품리뷰관리(평가)는 서로 다른 관심사로 독립적으로 판단한다 — 예: ON_SALE 상태(상품관리)여도 출시일이 안 지났으면 노출 안 됨(전시관리), 리뷰가 없어도 판매·노출에는 영향 없음 |

# Part I. 상품관리 정책

> 상품의 등록부터 검수, 판매, 변경, 판매종료까지 상품 생명주기와 운영 기준을 정의한다.

## 1.1 상품관리 기본 정책

- **생명주기**: 상품은 등록(1.5) → 검수·승인(1.6) → 판매(1.9) → 변경(1.11) → 종료(1.11)
  순서로 관리되며, 등록 경로(직매입/입점형)와 무관하게 동일한 생명주기 모델을 공유한다(원칙②·③).
- **상품 식별 기준**: 상품은 `productId`(ULID)로 식별되는 1개 row이며, 옵션이 있으면
  SKU(`skuId`) 단위로 재고·옵션값을 하위 관리한다(1.4).
- **상품·판매정보 구분**: "상품"은 이름·카테고리·이미지·정가·공급가 등 변경 빈도가 낮은
  마스터 성격 속성이고, "판매정보"는 판매가(1.7.2 기간별 스케줄)·상태(1.9)·재고(1.10)처럼
  변경 빈도가 높은 변동 성격 속성이다. 이 구분은 데이터 저장 방식(마스터 테이블 vs 이력성
  테이블)에도 그대로 반영된다.

## 1.2 상품분류 정책

### 1.2.1 계층 구조

대분류-중분류-소분류 3단계 계층으로 운영한다. 상품은 대표 카테고리 1개(소분류, 최하위)에만 귀속하는 것을 원칙으로 하며, 다중 카테고리는 허용하지 않는다. 
세분화된 검색·필터링은 카테고리가 아니라 태그·속성으로 처리한다.

> 이 "표준 카테고리"는 §2.5의 "전시 카테고리"와 다른 엔티티다 — 상품 분류(이 절)는 상품관리
> 소관, 고객 화면 노출 분류는 전시관리 소관이다(0.3 용어 정의 참조).

### 1.2.2 카테고리별 필수 입력 속성

대분류별로 필수 입력 속성이 다르다(예: 러닝화는 브랜드·성별·사이즈·드롭·용도, 보충제는
브랜드·제품유형·용량·인증여부). 구체적인 카테고리·속성 목록은 `DF-도메인모델ERD/catalog.md`
작성 시 전체 매트릭스로 확정한다(§6 Human Review).

이 속성 값은 상품 등록 시 입력값이자, 동시에 **검색 필터 조건으로 재사용**된다 — 별도의
필터 전용 속성 세트를 두지 않고, 카테고리별 속성 매핑(`cat_category_attribute`)을 그대로
Search 도메인에 색인 데이터로 제공해 필터 UI를 구성한다.

## 1.3 상품정보 관리 정책

### 1.3.1 필수/선택 입력 항목

| 구분 | 항목 | 필수 여부 |

| 필수 | 상품명, 표준 카테고리, 정가, 공급가, 대표 이미지 1장 | 필수 |
| 선택 | 상품 요약, 상품 설명, 추가 이미지, 카테고리별 속성값(1.2.2), 출시일(`release_date`), 판매자 상품코드(1.3.6) | 선택 |

### 1.3.5 콘텐츠 가드레일

상품명·설명·태그 전반에 적용되는 콘텐츠 작성 제약이다.

| 항목 | 정책 |
|---|---|
| 의료적 효능 표현 금지 | 질병 예방·치료 효능을 단정하는 표현 금지(건강기능식품법·식품위생법 — 특히 보충제·영양식품 카테고리) |
| 과장광고 금지 | 표시·광고의 공정화에 관한 법률 기준의 과장·허위 광고 표현 금지 |
| 비방·비교 금지 | 타사 상품·브랜드에 대한 비방 또는 직접 비교 표현 금지 |

| 처리 방식 | 등록·수정 시 자동 필터 적용 + 1.6(심사 정책) 심사 단계에서 2차 확인 |

### 1.3.6 판매자 상품코드

| 항목 | 정책 |
|---|---|
| 필드 성격 | 선택 입력. 플랫폼 PK(`productId`)와는 별개로, 판매자 자체 ERP·정산 대사용 식별자 |
| 검색·필터 사용 여부 | 사용하지 않음(내부 참고용) |

### 1.3.7 상품번호·옵션번호 채번규칙

플랫폼 PK(`productId`/`skuId`, ULID)와는 별개로, 사람이 식별·구술하기 쉬운 표시용 번호를
상품·옵션 각각에 부여한다. 

| 항목 | 규칙 |
|---|---|
| 상품번호 구성 | 8자리 전역 일련번호 + 3자리 랜덤번호 = 총 11자리. 접두어 없음 |
| 전역 일련번호 | 10,000,000부터 시작해 상품 등록마다 1씩 증가하는 전역 시퀀스(전체 판매자·직매입 공통, 리셋 없음) |
| 랜덤번호 역할 | 순번 추측 방지(총 등록 상품수 노출 차단) 목적의 난수(0~999). 유일성은 일련번호 부분이 이미 보장하므로, 랜덤번호 자체의 중복 여부는 검증하지 않음 |
| 옵션번호 구성 | 상품번호(11자리) + 3자리 일련번호 = 총 14자리 |
| 옵션 일련번호 | 상품 내 SKU 생성 순서대로 1부터 1씩 증가(001, 002, …) |
| PK 대체 여부 | 대체하지 않음 — `productId`/`skuId`(ULID)가 계속 PK이며, 상품번호·옵션번호는 조회·CS·정산 등에서 사용하는 표시용 식별자 |

### 1.3.8 상품정보제공고시 (전자상거래법)

> 항목이 다르다**(1.2.2 카테고리별 필수 입력 속성과 같은 구조). 아래는 이 플랫폼의 주요

| 대분류 | 고시 항목(예시, 법무 확인 전) |

| 항목 | 정책 |

### 1.4.1 옵션값 이미지 (2026-11-09 신설)

> **배경**: 색상 등 1단계 옵션은 보통 각 값마다 대표 썸네일(스와치)을 두어 상품 상세에서
> 색상 선택 시 보여주는 것이 오픈마켓 일반 관행이다. 사이즈 등 2단계 옵션은 이런 용도가

| 항목 | 정책 |
|---|---|
| 적용 대상 | 옵션그룹 1단계(depth=1)의 옵션값에만 허용 (예: 색상) |

## 1.7 가격·수수료 정책

### 1.7.1 가격 구조

```
정가(price_original) ≥ 판매가 ≥ 판매자 공급가(price_supply)
```

| 가격 유형 | 결정 주체 | 고객 노출 | 용도 | 저장 위치 |
|---|---|---|---|---|
| 정가 | 판매자 또는 플랫폼 MD | 노출(의무, 할인 전 기준) | 최초 판매가이자 할인율 표시 기준 | 상품 마스터(불변 성격) |
| 판매가 | 정가에서 파생(판매자가 별도로 설정하지 않음) | 노출 | 실제 노출 가격 | 정가 또는 1.7.2 할인가 테이블의 유효 행 |
| 판매자 공급가 | 판매자 | 미노출 | 정산 계산 기준 | 상품 마스터(불변 성격) |

`cat_product_price_schedule`(1.7.2)에 해당 상품의 유효한 할인 행이 없으면 판매가는 정가와 같다. 유효한 할인 행이 있으면 그 행의 할인가가 판매가가 된다.

목록과 상세는 할인가를 받아오는 경로가 다르다(1.7.4) — 
목록은 `cat_product_price_schedule`을 조회 시점에 join해서 노출하고, 상세는 Promotion에 실시간 동기 조회해서 노출한다. 
그 결과 목록(배치 지연 있음)과 상세(실시간)의 노출 가격이 짧은 시간 동안 다를 수 있다. 
쿠폰·회원등급할인·장바구니할인·포인트 사용(2.8)이 추가로 적용되면 최종 결제금액은 판매가보다
더 낮아질 수 있다.

### 1.7.2 할인가 배치 테이블 (`cat_product_price_schedule`)

| 항목 | 정책 |
|---|---|
| 테이블 소유 | Catalog |
| 데이터 생성 책임 | Promotion — 배치 주기마다 상품별 할인 정보를 일괄 적재한다 |
| 적재 단위 | 배치 1회 실행마다, 배치 주기 길이만큼의 유효 구간(`start_at`~`end_at`)을 가진 행 1건을 적재 |
| 저장 항목 | 상품코드, 시작일시, 종료일시, 최대할인율, 최대할인여부, 사은품여부, 다중할인여부 |
| 최대할인율 | 해당 상품에 적용 가능한 할인(단일할인·수량할인 등)을 모두 비교해 Promotion이 계산한 최댓값. 상품당 유효 행은 항상 0~1건이다 |
| 최대할인여부 | 해당 행이 최대할인율을 나타내는 행임을 표시 |
| 사은품여부·다중할인여부 | 할인가 계산과 무관한 뱃지 노출용 속성 — Promotion이 정한 값을 그대로 전달 |
| 유효 행 판정 | 조회 시점에 `start_at ≤ now < end_at`인 행을 유효 행으로 판정 |
| 행사 종료 처리 | 별도 종료 처리 없음 — 배치가 더 이상 신규 행을 적재하지 않으면 마지막 행의 `end_at` 경과로 자동 소멸 |
| 판매가 계산 | 판매가 = 정가 × (1 − 최대할인율) |

### 1.7.3 수수료 정책

최종 수수료율 = 카테고리 기본 수수료율 − 판매자 등급별 감면율.

구체적인 카테고리별 기본 수수료율·등급별 감면율 테이블은 `DF-도메인모델ERD/catalog.md` 작성시 확정한다(정책 존재는 확인됨, §6 Human Review).

### 1.7.4 상품-행사 가격 연동 (Promotion 연동 경계)

> **소유 도메인 안내**: 행사가·수량할인 등 할인 정책의 정의·규칙 (혜택유형·혜택조건·혜택방법·중복정책)은 **Promotion이 1차 소유**한다(`DBA-도메인정책서/promotion.md` §2.1~2.7). 
Catalog는 그 결과가 상품 데이터에 어떻게 반영되는지만 다룬다(D6A Q13~Q15, 2026-10-14 확정).

| 연동 지점 | Catalog의 역할 |
|---|---|
| 목록 조회 시 할인가 노출 | `cat_product_price_schedule`을 조회 시점에 join해서 노출 |
| 상세 조회 시 할인가 노출 | Promotion에 실시간 동기 조회해서 노출 — 목록과 경로가 다름 |
| 행사 시작·종료 처리 | Promotion 내부 소관 — Catalog는 관여하지 않는다 |
| 수량할인 그룹핑 | 상품 속성값(`vendor_id`·정가)을 Promotion에 제공, 그룹 판정은 Promotion이 수행 |

## 1.8 판매상품·판매조건 정책

상품은 **1 product = 1 vendor** 구조다 — 상품 row 자체가 특정 판매자에 귀속되며, 동일 상품을 여러 판매자가 공유하거나 각자 판매정보(가격·재고·설명·이미지)로 등록하는 멀티셀러 구조는 지원하지 않는다. 
판매자마다 가격·재고·설명·이미지가 다를 수 있으므로, 판매자별로 항상 별개의 상품으로 등록한다.

| 항목 | 정책 |
|---|---|
| 판매 가능 조건 | 상품 상태가 `ON_SALE`이고, `release_date` 노출 게이트(2.4)를 통과해야 실제 구매 가능 |
| 판매기간 | 별도 "판매 시작/종료일" 필드는 없음 — 상태 전이(1.9)로 판매 가능 여부를 제어 |
| 판매 중지 | 1.11(상품 변경·종료 정책) 참조 |

### 주문 수량 제한

| 항목 | 정책 |
|---|---|
| 적용 단위 | 상품 단위 — 한 상품에 속한 모든 SKU(옵션)의 수량을 합산해서 1회 주문 내 최대 수량을 제한 |
| 필드 | `cat_product.max_order_quantity` (nullable) |
| 기본값 | NULL(무제한) — 판매자가 필요한 상품에만 선택적으로 설정 |
| 검증 주체 | Catalog는 값만 제공하고, 실제 검증은 Order가 주문서 작성·결제 직전에 수행(`order.md` §2.4.2가 이미 전제하는 흐름) |
| Promotion 수량조건과의 관계 | Promotion의 수량할인 혜택조건(최소~최대 구매 수량 구간, 1+1처럼 min=max 고정값 포함, `promotion.md` 혜택조건 참조)은 Promotion이 대상 상품을 조회·등록하는 시점에 이 `max_order_quantity`와 비교해, 조건을 만족할 수 없는 상품(예: max_order_quantity=1인 상품은 min=2인 1+1 대상에서 제외)은 애초에 대상 리스트에 노출하지 않는다. Catalog는 값만 제공하고 필터링 로직은 Promotion이 수행 |

## 1.9 상품·판매 상태관리 정책

| 상태 | 코드 | 설명 |
|---|---|---|
| 임시저장 | `DRAFT` | 등록 중, 미제출 |
| 심사요청 | `REVIEW_REQUESTED` | 판매자 제출 완료 (입점형 전용) |
| 심사중 | `UNDER_REVIEW` | 플랫폼(MD) 검토 중 (입점형 전용) |
| 판매중 | `ON_SALE` | 정상 판매 |
| 품절 | `SOLD_OUT` | 재고 0 또는 수동 설정 |
| 판매종료 | `DISCONTINUED` | 영구 판매 중단 |
| 반려 | `REJECTED` | 심사 탈락 (입점형 전용) |

**경로별 전이**

```
[입점형]  DRAFT → REVIEW_REQUESTED → UNDER_REVIEW → ON_SALE
                                              ↓
                                          REJECTED → DRAFT (재심사)

[직매입]  DRAFT ─────────────────────────────────→ ON_SALE
          (REVIEW_REQUESTED·UNDER_REVIEW·REJECTED 미사용 — 심사 게이트 생략)
```

> 상태값 종류는 등록 경로와 무관하게 동일하다. 
> 다만 `REVIEW_REQUESTED`·`UNDER_REVIEW`·`REJECTED` 3개 상태는 입점형(`vendor.is_platform_direct=FALSE`)에만 유효하다. 
> Single Source of Truth는  `DH-상태머신/catalog.md`.

## 1.10 재고·구매조건 연계 정책

> **정책**: 발생 원인과 무관하게 재고 1 이상 복원 시 MD 확인 없이 자동 `ON_SALE` 전환한다
> (AS-IS 정책서 §3.1의 "담당자 확인 후 수동 전환" 방식에서 변경). 대안 비교·결정 사유는
> `DO-ADR(Catalog).md` ADR-C004 참조.

| 이벤트 | 재고 변화 | 상태 변화 | 처리 주체 |
|---|---|---|---|
| 주문 발생 | 차감 | 재고 0이면 `SOLD_OUT` 자동 전환 | 시스템 |
| 주문 취소 | 복원 | `SOLD_OUT` → `ON_SALE` 자동 전환 | 시스템 |
| 반품·교환 확정 (검수완료) | 복원 (+1) | `SOLD_OUT` → `ON_SALE` 자동 전환 (재고 1 이상 시) | 시스템 |
| 반품·교환 확정 (검수불합격) | 유지 (복원 없음) | 상태 변화 없음 | 시스템 |
| 판매자 재고 신규 등록(+N) | 증가 | `SOLD_OUT` → `ON_SALE` 자동 전환 (재고 1 이상 시) | 시스템 (MD 확인 불필요) |
| 판매종료 처리 | 무관 | `DISCONTINUED`로 수동 전환만 허용 (재고 수량과 무관한 별도 의사결정) | 판매자 또는 관리자 |

`cat_sku`에는 누적 판매량 컬럼 `sold_quantity_total`을 둔다(마스터 테이블인 `cat_product`가
아니라 재고와 같은 변동성 테이블에 둔다 — 2.6 판매량순 정렬에 사용). 위 표의 재고 변화와
같은 트랜잭션에서 함께 갱신한다 — 주문 발생(RESERVE) 시 `+`, 주문 취소·반품 확정(검수완료)
시 `-`, 판매자 재고 신규 등록(RESTOCK_VENDOR)은 영향 없음. 상품 단위 판매량은 소속 SKU의
`sold_quantity_total` 합산값이다.

### 재고 품절 임박 알림

| 항목 | 정책 |
|---|---|
| 기준수량 설정 단위 | 상품 단위 — 상품에 속한 모든 SKU에 동일 기준값 적용. 판매자가 상품별로 직접 설정 가능, 기본값 5 |
| 트리거 조건 | 상품에 속한 SKU 중 하나라도 `available_quantity`가 기준값 이하로 떨어지면 알림 |
| 수신 대상 | 입점형 상품은 해당 입점사 담당자에게 개별 발송. 직매입 상품은 플랫폼 공통 관리자 화면(타 도메인 소관 계정체계)에 등록된 관리자(MD/MD-OPERATOR)에게 발송 — Catalog는 별도의 담당자 지정 기능을 두지 않고, 임박 트리거 발생만 담당한다 |
| 발송 방식 | 상품 단위로 개별 발송(여러 상품을 묶어 한 번에 보내지 않음) |
| 채널 | Notification 도메인 연계 |
| 중복 발송 방지 | 같은 상품이 임박 상태를 유지하는 동안 재발송하지 않는다. 기준값 초과로 회복된 후 다시 기준값 이하로 떨어지면 재발송한다 |
| 품절(SOLD_OUT) 알림과의 관계 | 별개 이벤트 — 임박 알림은 사전 경고일 뿐이며, 품절 자체는 기존 1.9·1.10 상태 전이로 처리(상태 전환 자체에는 알림 없음) |

### 재입고 알림

> 재고 품절 임박 알림(위)과는 성격이 다른 별개 기능이다 — 임박 알림은 품절 **전** 내부
> 운영자(판매자·관리자)에게 보내는 예방용 알림이고, 재입고 알림은 품절 **후** 재입고 시점에
> 외부 고객에게 보내는 판매 기회 알림이다. `cat_restock_subscription`으로 이미 EARS·ERD에
> 반영돼 있던 기능을 이번에 DBA 정책서에 소급 반영한다(REQ-CAT-032).

| 항목 | 정책 |
|---|---|
| 신청 단위 | SKU(옵션) 단위 — 고객이 품절(`SOLD_OUT`)된 SKU마다 개별적으로 신청(`cat_restock_subscription`) |
| 신청 자격 | 로그인 고객. 1개 SKU당 1건만 유효(중복 신청 방지), 상태는 `PENDING`/`NOTIFIED` |
| 신청 가능 조건 | 해당 SKU가 `SOLD_OUT` 상태일 때만 신청 가능 (`ON_SALE` 상태인 SKU는 신청 메뉴 자체가 노출되지 않음) |
| 발송 트리거 | 1.10 재입고 자동전환(`SOLD_OUT → ON_SALE`, 재고 1 이상 복원) 발생 시, 해당 SKU의 `PENDING` 신청 건 전체를 `NOTIFIED`로 전환하며 일괄 발송 |
| 발송 채널 | Notification 도메인 연계 |
| 재알림 여부 | `NOTIFIED` 전환 후 해당 신청은 종료(재사용 안 함) — 다시 품절되면 고객이 재신청해야 함 |

## 1.14 찜하기(위시리스트) 정책

> **소유 도메인 결정**: 구조적으로는 Member가 "회원별 찜 목록"을 소유하는 편이 더 깨끗하지만,
> 찜 표시·해제가 상품 노출 상태(품절·단종 등)와 실시간으로 강하게 결합되는 데이터라 **Catalog가
> 직접 소유**하기로 확정했다(2026-11-06, 사용자 확인). Part III 리뷰·1.10 재입고 알림과 동일한
> 패턴 — `member_id`는 참조값으로만 저장하고, 회원 자격·탈퇴 등 회원 자체 관리는 Member 소관이다.
> D6A 인터뷰 범위 밖의 신규 기능이다.

| 항목 | 정책 |
|---|---|
| 데이터 단위 | 상품(product) 단위 `cat_product_wishlist` — 상품당 회원 1건, 중복 찜 불가 |
| 신청 자격 | 로그인 회원만 가능 |
| 노출 위치 | ① 상품이 노출되는 모든 목록 화면(Part II 전시 영역 포함)에 찜 여부 표시 ② 상품 상세에 찜 여부 표시 ③ 마이페이지에 "찜한 상품" 목록 제공 |
| 품절·판매종료 시 처리 | 상품이 `SOLD_OUT` 또는 `DISCONTINUED`로 전환되면 해당 상품의 찜 데이터를 즉시 제거한다 — 재입고돼도 복원되지 않으며, 고객이 다시 찜해야 한다 |
| Member와의 경계 | Catalog는 `member_id`만 외부 참조로 저장한다. 회원 탈퇴 시 찜 데이터 정리는 Member의 탈퇴 이벤트를 Catalog가 구독해 처리해야 하는데, 이 이벤트 연동의 실제 구현 여부는 §6 Human Review 대상(work-scope상 Member 쪽 확인 불가) |

## 1.15 최근 본 상품 정책

> D6A 인터뷰 범위 밖의 신규 기능이다(2026-11-06, 사용자 확인). 찜하기(1.14)와 달리 서버
> 영속화·회원 소유 데이터 구조를 두지 않는다 — 상품 상세 조회마다 기록되는 고빈도 쓰기라

> 종속적인 설계와 맞지 않는다.

| 항목 | 정책 |
|---|---|
| 저장 위치 | 클라이언트(브라우저 로컬스토리지/앱 로컬 저장) — 로그인 여부와 무관하게 동일 방식, 서버 영속화 없음 |

| 향후 확장 지점 | 기기 간 동기화가 필요해지면 서버 저장(회원 소유)으로 전환 — 현재는 범위 아님 |

## 1.16 SNS 공유·URL 복사 정책

> 리워드(포인트 적립 등) 없는 단순 공유 기능이다(2026-11-06, 사용자 확인, D6A 범위 밖 신규).

| 항목 | 정책 |
|---|---|
| 적용 대상 | 상품 상세(Part I), 전시 페이지(Part II) — Catalog가 소유한 콘텐츠만. 이벤트 페이지는 Promotion 소유라 Catalog 범위 밖(Promotion 쪽에서 별도 정의 필요) |
| 제공 메타데이터 | 공유 URL(canonical), 제목, 대표 이미지, 요약 설명 — 기존 상품·전시 데이터에서 그대로 추출(신규 필드 없음) |
| 리워드 | 없음 — 공유 횟수 집계·포인트 적립 등 부가 기능을 두지 않는다 |
| 신규 데이터·API | 없음 — 기존 상품 상세·전시 페이지 조회 API 응답에 메타데이터 필드만 포함 |

## 1.17 상품 랭킹 집계 정책 (2026-11-09 신설)

> 2.13(전시관리, 랭킹 조회·노출)과 짝을 이루는 정책이다. 이 섹션은 "집계(쓰기)"를, 2.13은
> "조회(읽기)"를 다룬다 — 1.10의 `sold_quantity_total`(전체기간 누적)과는 목적이 다른
> 별도 지표다. `sold_quantity_total`은 재고·매출 정합성을 위한 정확한 누적치이고, 이 랭킹
> 집계는 "최근 얼마나 많이 선택되고 있는가"를 보여주는 트렌드 지표라 집계 대상이 다르다.

| 항목 | 정책 |
|---|---|
| 데이터 모델 | `cat_product_sales_hourly(product_id, sale_hour, quantity)` — 상품×시간(1시간 truncate) 단위 버킷. PK(product_id, sale_hour) |
| 집계 대상 | `StockChanged` 이벤트의 `changeType`이 `RESERVE`(판매, +)·`RESTORE_ORDER_CANCEL`(주문취소, −)인 경우만 반영 |
| 집계 제외 대상 | `RESTORE_RETURN_EXCHANGE`(반품·교환 확정)·`RESTOCK_VENDOR`(판매자 재고 신규등록) — 반품은 처리 사이클이 길어(배송완료→수령→반품신청→수거→검수완료, 수일~2주) 원 판매 시점과 멀리 떨어진 날짜의 버킷을 뒤늦게 깎는 비대칭이 생기므로 제외(사용자 확인, 2026-11-09). 교환도 같은 이벤트로 묶여 있어 함께 제외 |
| 처리 시점·방식 | **비동기** — `StockService.reserve()`/`restore()`가 재고·`sold_quantity_total`을 갱신하는 트랜잭션과는 분리된다. 그 트랜잭션 커밋 후 발행되는 `StockChanged` 이벤트를 Catalog 자신이(도메인 내부 구독) 비동기로 수신해 집계한다 — 재고 트랜잭션의 지연·장애와 랭킹 집계 장애를 서로 격리하기 위함(사용자 확인, 2026-11-09) |
| 멱등성 | 기존 `ProcessedEventRepository` 패턴 재사용 — eventId 기준 중복 처리 방지 |
| 보존 기간 | 14일 (실시간·일간·주간 조회에 필요한 최대 범위는 7일이나 여유를 둠) — 저빈도 정리 배치로 만료분 삭제 |

# Part II. 전시관리 정책

> 상품·콘텐츠·기획전을 고객에게 어떤 구조와 조건으로 노출할지 정의한다. **상품의 판매 가능
> 여부를 결정하는 정책(Part I)과 실제 전시 노출 여부를 결정하는 정책(이 Part)은 구분된다**
> (0.4 원칙⑦).

## 2.1 전시관리 기본 정책

- **전시 운영 원칙**: 전시는 MD가 수동으로 구성·운영하는 영역(런칭 시점)과, 운영 안정화 후
  점진적으로 자동화(AI 스코어링)하는 영역으로 나뉜다(2.6).
- **전시 대상**: Part I에서 노출 게이트를 통과한 상품(ON_SALE이면서 `release_date ≤ now`)만
  전시 대상 후보가 된다(2.4).
- **전시와 판매의 관계**: 노출 게이트는 "노출 대상 집합"을 정하는 선행 단계이며, 노출
  순서(정렬)를 정하는 로직이 아니다. 즉 전시에서 빠진다고 판매가 막히는 것은 아니고(딥링크로
  접근 시 구매 가능, 2.4), 전시가 되더라도 재고가 없으면 품절로 표시될 뿐 전시 자체가 막히는
  것은 아니다.

## 2.2 전시 구조 관리 정책

MD가 수동으로 편집하는 전시 영역은 다음 5가지다: 메인 기획전·배너, 카테고리별 추천 상품,
신상품 상단 고정, MD 추천 큐레이션, 판매자 광고 계약 기반 노출 위치.

전시 콘텐츠의 콘텐츠유형·전시유형 정의는 2.3, 콘텐츠유형별 resolve 방식은 2.9, 전시 페이지
(`cat_display_page`) 단위 구성은 2.7에서 각각 다룬다.

## 2.3 전시 콘텐츠 관리 정책

전시 콘텐츠는 **콘텐츠유형**(노출 대상)과 **전시유형**(노출 방식) 2축 코드로 관리한다.
두 코드 모두 향후 추가될 수 있는 확장 코드다.

| 콘텐츠유형 | 등록 주체 | 비고 |
|---|---|---|
| 배너 | MD 직접 등록 | 전시 페이지 편집 화면에서 등록 |
| 이벤트목록 | Promotion 동기화(2.8) | MD가 직접 등록하지 않음 — 이벤트 key만 지정 |
| 상품목록 | MD가 상품코드만 등록 | 이미지·링크 resolve 방식은 2.9 참조 |
| 추천영역 | MD가 등록할 콘텐츠 없음(위치만 배치) | 연관상품 추천 위젯 정책은 2.9 참조 |
| 카테고리그리드 | MD 직접 등록 | 카테고리 단위 썸네일 그리드 |

| 전시유형 | 설명 |
|---|---|
| 목록형 | 콘텐츠를 격자·리스트 형태로 나열 |
| 스크롤형 | 콘텐츠를 가로·세로 스크롤로 나열 |
| 배너형 | 콘텐츠를 배너 이미지 형태로 노출 |

콘텐츠유형별로 허용되는 전시유형은 다음과 같다.

| 콘텐츠유형 | 허용 전시유형 |
|---|---|
| 배너 | 배너형만 |
| 이벤트목록 | 배너형, 스크롤형 |
| 상품목록 | 목록형, 스크롤형 |
| 추천영역 | 스크롤형만 |
| 카테고리그리드 | 목록형만 |

배너 콘텐츠유형의 이미지 용량은 파일당 최대 10MB(1.3.2 상품 이미지 용량과 동일). 해상도·
비율 등 그 외 규격은 두지 않는다.

## 2.4 상품 전시·노출 정책 (출시일 노출 게이트)

> **정책**: 상품 상태는 그대로 두고(1.9), 노출 조회(목록·검색·전시) 쿼리에서
> `release_date > now`인 상품을 필터링해 "예약 공개"를 구현한다. 대안 비교(상태 전이
> 추가 안, 검색 정렬 전용 한정 안의 탈락 사유)는 `DO-ADR(Catalog).md` ADR-C003 참조.

| 항목 | 정책 |
|---|---|
| 적용 상태 | `ON_SALE` 상품에만 적용 (DRAFT·REVIEW_REQUESTED 등은 애초에 비노출이라 대상 아님) |
| 게이트 조건 | `release_date > now`이면 노출 쿼리에서 제외 |
| 입력값 없을 때 처리 | 상품 등록 시 `release_date`를 입력하지 않으면 등록일시를 자동 입력한다(NULL로 저장하지 않음) — 즉시 `release_date ≤ now`가 되어 즉시 노출된다. 조회 쿼리는 `release_date > now` 조건 하나로만 필터링하면 되고, NULL 분기가 불필요하다 |
| 적용 범위 | 상품 목록, 검색 결과, 전시 영역(2.6 노출 우선순위 대상) |
| 상세 페이지 직접 접근(딥링크) | **차단** — 목록·검색과 동일하게 적용. `release_date > now`인 상품은 상세 URL 직접 접근도 비공개(허용 안 함) |
| 노출 전환 시점 | 별도 배치·이벤트 불필요 — 조회 시점에 `now`와 비교하므로 release_date 도달 즉시 자동 반영 |
| 판매(구매) 가능 여부 | 상세 페이지 접근 자체가 차단되므로, `release_date` 도달 전에는 구매 경로도 사실상 없음(상태는 이미 `ON_SALE`이지만 노출 게이트가 선행) |

## 2.5 전시 카테고리 정책

### 2.5.1 계층 구조 (3단계 트리)

표준 카테고리(1.2)와 전시 카테고리는 별도 엔티티다. 표준 카테고리는 상품이 귀속되는 분류
기준(상품관리 소관, 3단계 계층)이고, 전시 카테고리는 고객 화면의 메뉴·카테고리 그리드에
노출되는 분류 기준(전시관리 소관)이다.

전시 카테고리는 **대분류(depth=1) → 중분류(depth=2) → 소분류(depth=3)** 3단계 트리로
운영한다. 테이블 구조(`cat_display_category`, parent_id 자기참조)는 범용 트리를 그대로
유지한다.

| 항목 | 정책 |
|---|---|
| 깊이 | 3단계 고정 (대분류 → 중분류 → 소분류). 4단계 이상 생성 금지 |
| 상품 매핑 | **소분류(최하위)에만 매핑 가능.** 대분류·중분류에는 상품을 직접 매핑하지 않는다 |
| 상위 분류 화면 노출 | 대분류·중분류 조회 시 하위 소분류 전체에 매핑된 상품을 합산해서 노출(상위 분류 = 하위 소분류들의 집계 뷰) |
| 상위 분류 자체 콘텐츠 | 상품 매핑과 무관하게 이미지·설명 등 자체 메타데이터는 가질 수 있다 |

> **역할 정정(2026-11-09)**: 고객이 보는 "카테고리" 메뉴·목록 화면(mobile `/category`)은
> **전시 카테고리 기준**이다. 표준 카테고리(1.2)는 판매자 등록 시 분류·필수속성·수수료율
> 산정에만 쓰이는 내부 분류이며 고객에게 노출되지 않는다 — 이전까지 REQ-CAT-029·고객 상품
> 목록 API가 표준 카테고리로 잘못 연결돼 있었다(§6 HR #37 관련, 이번에 해소).

### 2.5.2 표준-전시 카테고리 매핑

표준 카테고리(소분류)와 전시 카테고리(소분류)는 **N:M**으로 매핑한다(`cat_standard_display_category_mapping`).
하나의 전시 카테고리에 여러 표준 카테고리 상품이 매핑될 수 있고, 반대로 하나의 표준
카테고리가 여러 전시 카테고리에 중복 노출될 수 있다. 상품 등록 시 선택한 표준 카테고리의
`is_default=TRUE` 매핑이 있으면 해당 전시 카테고리에 자동으로 매핑되고(`cat_product_display_category`),
MD·판매자가 추가 전시 카테고리를 수동으로 더 매핑할 수 있다.

> 중복 노출 시(여러 전시 카테고리에 동시 노출될 때) 각 전시 카테고리 화면 안에서의 정렬은
> 2.5.3에서 확정했다 — 전시 카테고리마다 독립적인 순서·고정 값을 가지므로, 같은 상품이라도
> 전시 카테고리별로 다르게 노출될 수 있다.

### 2.5.3 전시카테고리별 상품 정렬

> D6A 범위 밖 신규 기능이다(2026-11-09, 사용자 확인). 기존 2.6 노출 우선순위(MD Override)는
> 상품 1건당 전역으로 값을 하나만 가져 모든 화면에 동일하게 적용되는데, 전시 카테고리는
> MD가 직접 구성하는 큐레이션 영역이라 **카테고리마다 다른 순서**를 줄 수 있어야 한다는
> 요구가 있어 별도 메커니즘으로 분리했다 — `cat_product_display_category`(상품-전시 카테고리
> 매핑, 2.5.2)에 정렬·고정 값을 둔다.

| 항목 | 정책 |
|---|---|
| 정렬 기준 | `is_pinned`(상단고정) 내림차순 → `sort_order` 오름차순. 고정 상품은 정렬순서와 무관하게 항상 먼저 노출되고, 고정 상품이 여러 건이면 그들끼리는 `sort_order`로 다시 정렬 |
| 저장 방식 | 관리자(MD, 운영자)가 전시 카테고리를 선택해 소속 상품 목록을 조회한 뒤, 화면에서 마우스 드래그앤드랍으로 리스트 순서를 조정하고 저장한다. 저장 시점의 리스트 순서를 그대로 0부터 1씩 증가하는 `sort_order`로 일괄 저장(전체 교체) |
| 상단고정(`is_pinned`) | 목록의 각 행에 토글로 부여. 저장 후 재조회 시 고정 상품이 맨 위로 재배치됨(저장 화면에서의 위치와 무관) |
| 관리 화면 | 2.6 노출 우선순위 관리와는 별도의 메뉴·화면으로 분리한다 — 대상(카테고리 선택 필요)과 저장 방식(드래그앤드랍 전체 순서 저장 vs 개별 상품 수동 순위 입력)이 달라 같은 화면에 통합하지 않는다 |
| 적용 대상 | `cat_product_display_category`에 매핑된 상품만. 매핑 자체가 없는 상품은 이 화면에 나타나지 않는다(2.5.2 매핑이 선행 조건) |

> **[Human Review]** 이 정렬값을 실제로 소비하는 고객 화면(전시 카테고리별 상품 목록
> 조회)은 아직 별도로 설계되지 않았다 — 현재 고객 화면은 표준 카테고리(`cat_category`)
> 기준으로만 상품을 조회한다(REQ-CAT-029). 전시 카테고리 기준 고객 조회 화면·API가
> 필요한지는 후속 확인 필요.

## 2.6 상품목록·정렬 정책

### 추천순 (기본 정렬)

```
exposure_priority = COALESCE(md_override, sales_rank, default_order)
```

| 단계 | 방식 |
|---|---|
| 1단계 | MD 수동 노출 순서 설정 |
| 2단계 | 판매량 순위(`sales_rank`) — `cat_sku.sold_quantity_total`을 상품 단위로 합산한 값 기준(1.10) |
| 3단계(운영 안정화 후, 확장 지점) | AI 스코어링 배치 도입 시 `md_override`와 `sales_rank` 사이에 삽입 |

MD 수동 설정값은 항상 최우선 적용된다(MD Override 원칙, 0.4 원칙⑤). 둘 다 없으면 최신

## 2.10 전시 일정·게시 정책

전시 기간은 `display_start_at`(전시 시작일시)·`display_end_at`(전시 종료일시) 두 필드로
관리한다. PUBLISHED 상태에서도 섹션·일시를 직접 수정할 수 있다 — 별도 수정용 사본을 만들지
않고 저장 자체가 바로 반영된다(2.7.1 단순화 참조).

| 항목 | 정책 |
|---|---|
| 전시 시작(`display_start_at`) | 미래 시각으로 설정하면 그 시각 도달 시 배치가 `DRAFT`→`PUBLISHED`로 자동 전환(`BAT-CAT-002`). NULL이거나 이미 지난 시각이면 "즉시 게시" 클릭으로 바로 전환 |
| 전시 종료(`display_end_at`) | 설정하면 그 시각 도달 시 배치가 `PUBLISHED`→`CLOSED`로 자동 전환. NULL이면 수동 종료만 가능(기간 무제한) |
| 값 제약 | `display_end_at`을 설정하는 경우 `display_start_at`보다 이후여야 한다 |
| 값 형식 | `yyyy.mm.dd hh:mi:ss`(날짜는 점, 시각은 콜론 구분, 초 단위까지) — 2.8.2·1.7.2의 `start_at`/`end_at`을 포함해 Catalog의 "시작일시·종료일시" 쌍 컬럼 전체에 동일 적용 |
| 긴급 게시·회수 | `cat_display_page.is_exposed`(전시여부, 기본값 Y) 플래그로 처리. 노출 조건은 `status=PUBLISHED AND is_exposed=Y`(2.4 출시일 게이트와 동일한 "상태는 그대로 두고 조회 쿼리에서만 필터링" 패턴). 운영자가 즉시 N으로 전환해 노출을 끄고, 조치 후 Y로 되돌리면 즉시 복원된다 — 상태 전이·전시기간·홈 지정(`is_home`) 어느 것도 건드리지 않는다 |

> **[Human Review]** `yyyy.mm.dd hh:mi:ss` 표시 형식은 `C6-API설계컨벤션.md` §8.1에서 이미
> 확정한 전사 공통 포맷(`yyyy-MM-dd HH:mm` 목록·상세 표시, ISO 8601 전체 시각)과 구분자·초
> 단위 포함 여부가 다르다. 이번 지시는 Catalog의 "시작일시·종료일시" 쌍 컬럼에 한정해
> 적용했다 — 전사 컨벤션 자체를 바꿀지는 C6/C8 담당자 확인 필요.

홈으로 지정된(`is_home=TRUE`) 페이지가 `is_exposed=N`이 되면, 고객에게는 "홈 미지정" 상태와
동일하게 처리해 기본 카테고리 화면으로 대체 노출한다(`DK-세부유스케이스/catalog.md` 홈 화면
유스케이스의 "홈 미지정" Human Review와 함께 해소, 2026-11-06).

## 2.11 전시 검수·승인 정책

별도 검수·승인 단계를 두지 않는다. 전시 페이지는 **MD 자율 관리 영역**이라 상품 심사(1.6,
입점팀·MD 간 별도 승인 주체가 존재)와 다르게 승인권자가 따로 없다. MD가 작성한 페이지를
직접 `PUBLISHED`로 전환하며, 게시 후 문제가 발견되면 2.10의 전시여부(`is_exposed`) 플래그로
즉시 회수한다.

링크 오류(깨진 배너·섹션 링크)도 같은 원칙으로 자동 검증 없이 MD·운영자가 발견 시 수동
수정한다. 콘텐츠가 비어있는 섹션(빈 영역)은 노출 시 해당 섹션 자체를 생략(skip)한다 — 2.8.2
이벤트 배너의 eventKey 누락 시 "해당 배너만 제외, 나머지 섹션은 정상 노출"과 동일한 원칙이다.
이미지 규격 검증은 1.3.2를 따르고, 품절·판매종료 상품이 포함된 섹션은 1.9·2.4·1.10의 상품
노출 정책을 그대로 따른다 — 전시 전용 별도 기준을 두지 않는다.

## 2.13 상품 랭킹 조회·노출 정책 (2026-11-09 신설)

## 2.14 GNB 메뉴 관리 정책 (2026-11-09 신설)

| 항목 | 정책 |

| 데이터 모델 | `cat_gnb_menu(id, name, link_type, link_target, sort_order, is_exposed, display_start_at, display_end_at, created_by, created_at, updated_at)` — 단일 계층(서브메뉴 없음) |

## 2.15 비홈 전시 페이지 뷰어 정책 (2026-11-09 신설)

> "전시 페이지 뷰어(비홈) 화면 미설계" 미진항목(DQ #9·#13)을 해소한다. GNB(§2.14)의
> linkType=DISPLAY_PAGE, SNS 공유(§1.16)의 전시 페이지 공유 메타데이터(API-CAT-037b)가
> 공통으로 가리키는 "고객이 홈이 아닌 전시 페이지를 보는 화면"을 메운다.

| 항목 | 정책 |
|---|---|
| 적용 대상 | `cat_display_template`으로 섹션을 조합해 만든 **템플릿형 전시 페이지**(홈과 동일 구조) — 랭킹·카테고리 목록처럼 고정 UI 패턴을 가진 화면은 이 정책의 대상이 아니다(사용자 확인, 2026-11-09) |
| 섹션 resolve 로직 | 홈 화면(§2.9, REQ-CAT-053)과 **완전히 동일** — 홈도 결국 `is_home=true`인 `cat_display_page` 1건일 뿐이므로, 둘은 "같은 종류의 화면"이고 `is_home` 값만 다르다(사용자 확인) |
| 조회 가능 상태 | `status=PUBLISHED`이고 `is_exposed=TRUE`인 페이지만 — DRAFT·CLOSED·CANCELLED 또는 `is_exposed=FALSE`는 404 (홈이 `is_home=true && status=PUBLISHED`만 노출 대상으로 삼는 것과 동일 기준) |
| URL 식별자 | `cat_display_page.slug` — GNB의 `linkTarget`(DISPLAY_PAGE), SNS 공유 URL이 동일한 slug를 가리킨다 |
| 홈과의 차이 | `is_home` 여부만 다르다. 홈은 "현재 홈으로 지정된 1건"만 조회하고, 이 화면은 "slug로 지정한 특정 1건"을 조회한다 |

## 2.16 상품 단위 전시여부·검색노출 제외 (2026-11-09 신설)

> **배경**: 상품 상세 탭 구성을 검토하는 과정에서 "전시 탭"을 별도로 둘지 검토했으나,
> 토글 2개만으로는 탭 하나를 구성할 근거가 부족하다고 판단해 **독립 탭을 두지 않고
> 기본정보 탭에 통합**하기로 확정했다(사용자 확인, 2026-11-09). 상품이 소속된 전시
> 페이지 역참조 조회는 별도 설계 대상에서 제외한다.

| 항목 | 정책 |
|---|---|
| 상품 단위 전시여부(`is_exposed`) | 관리자(MD)·판매자가 상태(status)·재고와 무관하게 상품을 고객 조회에서 즉시 숨길 수 있는 수동 플래그. `cat_display_page.is_exposed`(§2.10)와 동일한 "상태 전이 없이 조회 쿼리에서만 필터링" 패턴 |
| 적용 범위 | 상품 목록(§2.5)·검색·전시 영역(§2.6)·상세 페이지 직접 접근(딥링크) 전부 차단 — 출시일 노출 게이트(§2.4)와 동일하게 딥링크도 예외 없음 |
| 단종(discontinue)과의 차이 | 단종은 영구적·비가역 상태 전이(1.9)이고, 이 플래그는 가역적인 임시 숨김이다. ON_SALE/SOLD_OUT 상태에서도 설정 가능 |
| 검색노출 제외(`is_search_excluded`) | 목록·카테고리·상세에는 정상 노출하되 **검색 결과에서만** 제외하는 보조 플래그 |
| 두 플래그의 관계 | 독립적 — `is_exposed=FALSE`면 검색도 당연히 제외되지만(상위 조건), `is_search_excluded`는 `is_exposed=TRUE`인 상품에 한해 검색만 선택적으로 끄는 하위 옵션이다 |
| 관리 화면 | 별도 탭 없이 상품 상세(관리) 기본정보 탭에 체크박스 2개로 노출 |

# Part III. 상품리뷰관리 정책

> 구매자의 리뷰 작성부터 보상, 검수, 노출, 신고 및 사후 관리까지 리뷰의 전체 운영 기준을
> 정의한다.

## 3.1 리뷰관리 기본 정책

- **관리 대상**: 상품 리뷰만 Catalog가 관리한다. Q&A(상품 문의)·Q&A 신고는 Community
  소유다(0.2 제외범위).
- **상품 귀속 기준**: 리뷰는 `productId` 1건에 N개 리뷰가 귀속되는 1:N 관계. SKU(옵션) 단위
  리뷰 구분은 두지 않는다.
- **운영 원칙**: 리뷰는 구매 경험에 대한 평가이므로, 작성 자격(3.2)이 "구매확정" 여부에
  근거한다는 것이 다른 커뮤니티형 콘텐츠(Q&A)와의 핵심적인 차이다.

## 3.2 리뷰 작성 자격 정책

| 항목 | 정책 |
|---|---|
| 작성 가능 회원 | 해당 상품을 구매한 본인 회원 (Member 연계) |
| 구매·주문 상태 조건 | 주문 구매확정 이후 작성 가능 (Order 연계 — `DB-도메인정의서.md` Context Map "구매확정 정보" 이벤트) |
| 상품별 작성 제한 | 1건의 구매(주문항목)당 리뷰 1건 |
| 작성 가능 기간 | 구매확정 후 30일 이내 |

## 3.3 리뷰 유형·작성 정책

| 리뷰 유형 | 설명 |
|---|---|
| 텍스트 리뷰 | 기본 유형, 모든 리뷰에 필수 |
| 포토 리뷰 | 이미지 첨부 — 텍스트에 추가로 첨부 가능 |
| 동영상 리뷰 | 동영상 첨부 — 텍스트에 추가로 첨부 가능 |

| 항목 | 제한 |
|---|---|
| 텍스트 글자수 | 최소 10자 ~ 최대 1,000자 |
| 포토 개수 | 최대 5장 |
| 포토 용량·형식 | 파일당 최대 10MB, JPG/PNG/WebP (1.3.2 상품 이미지 정책과 동일) |
| 동영상 개수 | 최대 1개 |
| 동영상 용량·재생길이·형식 | 최대 50MB, 최대 30초, MP4 |

## 3.4 리뷰 작성·수정·삭제 정책

| 항목 | 정책 |
|---|---|
| 작성 횟수 | 3.2(구매 1건당 1회)로 사실상 제한됨 |
| 수정 가능 기간·횟수 | 3.2의 작성 가능 기간(구매확정 후 30일 이내) 내에서 1회만 수정 가능 |
| 삭제 가능 조건 | 작성자 본인 삭제 가능. 삭제 시 3.6(보상) 회수 여부는 3.6 참조 |
| 재작성 기준 | 허용하지 않음 — 삭제 후에도 동일 구매(주문항목)에 대한 리뷰는 재작성할 수 없다 |

## 3.5 평점 관리 정책

| 항목 | 정책 |
|---|---|
| 평점 범위 | 1~5점 (정수) |
| 필수 여부 | 리뷰 작성 시 평점 필수 |
| 평균 평점 산출 | 상품에 귀속된 전체 유효(비블라인드) 리뷰의 단순 평균 |
| 재계산 시점 | 리뷰 작성·삭제·블라인드 처리 시 즉시 재계산(배치 아님) |

## 3.6 리뷰 보상 정책

> **소유 도메인 안내**: 포인트 등 보상의 지급 규칙(지급액·조건) 원본은 Member 또는
> Promotion 도메인 소관일 수 있다 — Catalog는 "리뷰 작성 완료"(`ReviewCreated` 이벤트)만
> 발행하고, 보상 지급 로직 자체는 소유하지 않는다.

| 항목 | 정책 |
|---|---|
| 보상 유형 | 리뷰 유형별(텍스트/포토/동영상) 차등 지급. 유형별 기본 포인트 금액은 **Member**가 관리자 설정화면에서 지정 — Catalog는 `reviewType` 분류만 제공, 금액은 알지 못한다 |
| 지급 조건·시점 | 리뷰 작성 완료 시 `ReviewCreated` 이벤트 발행(`reviewType`·`productId`·`memberId` 포함). Catalog는 금액·행사 여부를 조회·중계하지 않고 이벤트만 발행한다 — 이후 조회·지급 요청은 수신 도메인이 각자 수행한다 |
| 소유 구분 | **Member**가 `ReviewCreated`를 구독해 자신이 소유한 기본 포인트 정책을 적용, 자기 원장에 직접 지급한다. **Promotion**이 같은 이벤트를 구독해 자신이 소유한 행사 정책으로 해당 상품·기간의 리뷰적립 행사 여부·금액을 판단하고, 해당하면 금액·사유("리뷰작성 프로모션 적립")를 들고 Member의 포인트 지급 API를 명시적으로 호출한다 |
| 중복 지급 방지 | 3.4(재작성 불가 확정)로 해소 — 재작성이 없으므로 재지급 이슈 자체가 발생하지 않음 |
| 회수 기준 | 리뷰 삭제·블라인드 시 `ReviewDeleted`/`ReviewBlinded` 이벤트 발행 → **Member가 단독으로** 해당 리뷰에 지급된 포인트(기본+행사 추가분 전체)를 회수한다. 포인트 보유는 출처(기본/행사)와 무관하게 Member가 단일 원장으로 관리하므로 Promotion은 회수 이벤트를 구독하지 않는다 |

## 3.7 리뷰 검수 정책

| 항목 | 정책 |
|---|---|
| 처리 방식 | 작성 시 자동 필터(금칙어 등) + 운영자 사후 검수(3.11) |
| 금칙어 | 욕설·선정적 표현·개인정보 패턴(전화번호·이메일 등)·광고성 URL — 1.3.5 상품 콘텐츠 가드레일과 동일한 금칙어 사전 재사용(운영자가 관리하는 동적 리스트) |
| 개인정보·부적절 콘텐츠 | 전화번호·이메일 등 개인정보 패턴은 등록 시 자동 마스킹, 욕설·선정성 등은 금칙어 필터로 자동 차단. 필터를 통과한 애매한 건은 신고(3.8) 기반 사후 검수로 처리 |

> 광고·도배(동일 문구 반복 투고) 자동 탐지는 두지 않는다 — 리뷰는 구매(주문항목) 1건당
> 1개로 제한돼(3.2) 짧은 시간에 대량 반복 투고하는 패턴 자체가 성립하기 어렵다. 리뷰
> 1건 안에 광고성 문구가 들어가는 경우는 위 금칙어 필터(광고성 URL)로 이미 걸러지므로,
> 남는 애매한 사례는 운영자 사후 검수(3.11)로 충분하다.
