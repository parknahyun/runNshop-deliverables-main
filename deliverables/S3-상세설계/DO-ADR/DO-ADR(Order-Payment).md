## ADR-001: 재고 선점 방식

### 상태: 개정됨 (Amended, 2026-10-29) — 선점 시점은 ADR-007로 대체

> 개정 요지: 재고 선점 방식(일반=DB `SELECT FOR UPDATE`, 행사=Redis `DECR`)은 유효하다. 다만 "결제하기에서 동기로 선점"하던 시점은 폐기되고, 결제하기는 동기 접수(TEMP→STOCK_REQUESTED + 아웃박스 `STOCK_DEDUCT_REQUESTED`)만 수행하며 컨슈머가 재고를 차감한다(비동기 접수, ADR-007). 일부 SKU 부족은 실패 SKU만 재시도하고 3회 소진 시 복원 + `STOCK_FAILED`.

### 맥락

주문 결제 시 재고를 선점해야 하는데, 일반 상품과 행사 상품의 트래픽 패턴이 다르다.
일반 상품은 동시 주문이 적지만, 행사 상품은 특정 시간에 트래픽이 폭증한다.
재고 선점이 실패하면 결제 후 취소해야 하므로 UX가 크게 저하된다. *(당시 가정: 결제하기에서 동기 선점. 현행은 ADR-007.)*

### 결정

일반 상품은 DB `SELECT FOR UPDATE`, 행사 상품은 Redis `DECR`로 선점한다.
복원은 양쪽 모두 비동기(Outbox 이벤트)로 처리한다.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. DB FOR UPDATE 단일 | 구현 단순, 트랜잭션 보장 | 행사 상품 동시성 병목 | 초당 1000+ 요청 처리 불가 |
| B. Redis DECR 단일 | 높은 동시성 처리 | 장애 시 데이터 유실 위험, 복잡도 증가 | 일반 상품에 과잉 설계 |
| **C. 혼합 (채택)** | 상황별 최적, 일반은 단순·행사는 고성능 | 분기 로직 필요 | — |

### 결과

- 긍정: 일반 상품 단순성 유지 + 행사 상품 고성능 확보
- 부정: 재고 선점 로직에 분기 존재 (상품 유형 판별 필요)
- 주의: Redis 장애 시 DB fallback 전략 필요 (REQ-CAT-015 연계)

### 참여자

- 테크리드
- 주문 파트 시니어

## ADR-002: 결제 요청 방식 (동기 vs 비동기)

### 상태: 대체됨 (Superseded by ADR-007·ADR-008, 2026-10-29)

> 현행: 결제하기는 동기 접수만 하고, Payment 승인 요청은 `PAYMENT_REQUESTED` 이벤트 컨슈머가 비동기로 수행한다(ADR-007). PG 승인 응답 대기는 **3초**이며 무응답은 결제 확인 중(CONFIRMING)→PG 거래 조회로 확정한다(ADR-008). 아래 "동기 PublicApi·타임아웃 30초"는 결정 당시 값(이력)이다. 환불은 비동기로 유지하되 트리거는 단일화됐다(주문 취소 환불=ORDER_CANCELLED 이벤트 자동, 클레임 환불=어드민 [환불 처리] API-029 요청).

### 맥락

Order에서 Payment로 결제를 요청할 때, 동기(PublicApi 직접 호출)와 비동기(이벤트 발행 후 콜백 수신)
두 가지 방식이 가능하다. 고객이 결제하기 버튼을 누른 후 즉시 결과를 알아야 하는 UX 요구가 있다.

### 결정

결제 요청은 **동기(PublicApi)** 호출로 처리한다.
환불은 즉시 응답이 불필요하므로 비동기(이벤트)로 처리한다.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. 전부 동기 | 구현 단순, 즉시 결과 확인 | 환불 시 PG 응답 지연으로 UX 블로킹 | 환불에 부적합 |
| **B. 혼합: 결제=동기, 환불=비동기 (채택)** | 결제 즉시 결과 + 환불 비블로킹 | 두 가지 호출 패턴 공존 | — |
| C. 전부 비동기 | 도메인 간 결합도 최소 | 결제 결과 대기 UX 구현 복잡 (폴링/웹소켓) | 고객 대기 UX 과도하게 복잡 |

### 결과

- 긍정: 결제 시 즉시 성공/실패 피드백, 환불은 후속 처리로 깔끔
- 부정: Order→Payment 동기 의존 (Payment 장애 시 주문 불가)
- 주의: Payment 서비스 SLA 확보 필요 (타임아웃 30초, 재시도 3회)

### 참여자

- 테크리드
- 주문 파트 시니어
- 결제 파트 시니어

## ADR-003: 2계층 주문 구조 (플랫폼주문 → 판매자주문 분할)

### 상태: 승인 (Accepted)

### 맥락

고객이 여러 판매자 상품을 한 번에 결제하면, 배송·정산·클레임은 판매자 단위로 처리해야 한다.
"고객이 보는 주문 1건"과 "판매자가 처리하는 주문 N건"의 불일치를 어떻게 모델링할지 결정이 필요하다.

### 결정

`ord_platform_order`(고객 단위, 1:N) → `ord_order`(판매자별 처리 단위) 2계층 구조를 사용한다.
결제는 platform_order 단위(1회), 배송·정산·클레임은 order 단위로 처리한다.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. 단일 테이블 (1주문=1판매자 강제) | 모델 단순 | 여러 판매자 동시 구매 불가, UX 제한 | 마켓플레이스 기본 기능 불가 |
| **B. 2계층 (채택)** | 결제는 1회, 배송·정산은 판매자별 독립 | 테이블 2개 관리, 조인 비용 | — |
| C. 3계층 (주문그룹→주문→라인) | 더 세분화된 관리 | 과잉 복잡도, runNshop 규모에 불필요 | 오버엔지니어링 |

### 결과

- 긍정: 고객은 한 번에 결제, 판매자는 독립적으로 출고·배송·정산 처리
- 부정: platform_order↔order 금액 정합성 불변식 관리 필요
- 주의: 부분취소/부분환불 시 금액 안분 로직 복잡도 증가

### 참여자

- 테크리드
- DBA
- 기획자

## ADR-004: PG 결제 실패 시 재시도 정책

### 상태: 개정됨 (Amended, 2026-10-29) — 지수 백오프·30초는 폐기, ADR-008 반영

> 현행 값: 승인 응답 대기 **3초**, 재시도 간격 **3초 고정**(지수 백오프 폐기), 승인 실패 응답·3초 무응답(거래 조회 미승인 확정)은 **최초 시도 포함 총 3회 시도**(재시도 최대 2회)이며 누적 실패 3회 도달 시 `CANCELLED` + `PAYMENT_FAILED`(정책서 payment.md 4.5.2·9.6.1). 자동 재시도는 같은 행·같은 멱등키·`pay_group_no` 불변, 고객 재결제는 새 `pay_group_no`. 이하 본문은 결정 당시(이력)이다.

### 맥락

PG(토스페이먼츠) 승인 요청이 네트워크 이슈·일시 장애로 실패할 수 있다.
고객에게 재시도를 맡기면 UX가 나빠지고, 무제한 자동 재시도는 PG 과부하를 유발한다.

### 결정

PG 승인 실패 시 **최대 3회 자동 재시도** (지수 백오프: 1초→2초→4초), 타임아웃 30초.
3회 실패 후 결제 취소(PAYMENT_FAILED) 처리하고 고객에게 재주문 안내.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. 재시도 없음 (즉시 실패) | 구현 단순 | 일시적 장애에도 결제 실패 → 이탈률 증가 | 고객 경험 저하 |
| **B. 3회 재시도 (채택)** | 일시 장애 복구 가능, PG 권장 사항 준수 | 최대 ~7초 대기 (1+2+4) | — |
| C. 5회 이상 재시도 | 복구 확률 증가 | 고객 대기 시간 과다 (15초+), PG 과부하 | 대기 시간 > 30초 타임아웃 |

### 결과

- 긍정: 일시적 PG 장애 자동 복구, 토스페이먼츠 권장 정책 준수
- 부정: 최대 7초 대기 발생 (로딩 스피너 필요)
- 주의: `pg_transaction_id`로 멱등 보장, 중복 승인 방지

### 참여자

- 결제 파트 시니어
- 테크리드

## ADR-005: 카드번호 미저장 (PG 토큰화)

### 상태: 승인 (Accepted) — 로그 저장 전제는 2026-10-29 개정

> 개정 요지: 토큰화 결정은 유효하다. 다만 PG 로그는 **응답 문자열 자체를 개인정보 마스킹 후 `raw_response`에 저장**하고, **요청은 원문을 저장하지 않으며** 시각·구분·금액·`pg_transaction_id`·reason만 남긴다(`ord_status_history`에도 원문 없음).
> PG 로그 마스킹(2026-11-03, 정책서 11.3.4): 대상은 정책서 11.3.4와 같고(수령인·연락처·주소·환불계좌·주문자명·가상계좌·카드), 저장 시점에 즉시 마스킹하며 보관 기간은 주문 정보와 같다(삭제 없음). Order 배치의 `pay_payment` 마스킹은 PaymentPublicApi(API-060)로 요청해 도메인 경계를 유지한다.

### 맥락

고객 결제수단 등록 시 카드번호·CVV를 서버에 저장할지, PG 토큰만 보관할지 결정이 필요하다.
PCI DSS 인증 없이 카드 정보를 저장하면 법적·보안 리스크가 발생한다.

### 결정

카드번호·CVV는 **서버에 저장하지 않는다**. PG(토스페이먼츠)가 발급하는 빌링키(토큰)만 보관한다.
화면에는 마스킹된 표시명(`****-1234`)만 노출한다.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. 카드번호 직접 저장 (암호화) | 자체 결제 처리 유연성 | PCI DSS 인증 필요, 유출 시 대형 사고 | 인증 비용·리스크 과다 |
| **B. PG 토큰화 (채택)** | PCI DSS 부담 없음, PG가 보안 책임 | PG 의존도 증가, PG 변경 시 토큰 마이그레이션 | — |

### 결과

- 긍정: 보안 리스크 최소화, NFR-SE-08(PCI DSS) 준수
- 부정: PG 변경 시 토큰 재발급 마이그레이션 필요
- 주의: pay_payment_log의 raw_response(PG 응답 문자열 자체, 2026-10-29 확정)에도 카드번호 포함 금지 (PII 마스킹 적용). 요청 원문은 저장하지 않는다

### 참여자

- 테크리드
- 보안 담당

## ADR-006: 도메인 간 이벤트 전달 방식 (Outbox 패턴)

### 상태: 승인 (Accepted)

### 맥락

ORDER_CANCELLED, CLAIM_COMPLETED 등 도메인 간 이벤트를 전달할 때,
직접 메시지 브로커(Kafka)에 publish하면 DB 트랜잭션과 이벤트 발행의 원자성이 깨질 수 있다
(DB는 커밋됐는데 이벤트 발행 실패, 또는 그 반대).

### 결정

**Outbox 패턴**을 사용한다. 이벤트를 별도 outbox 테이블에 INSERT(같은 트랜잭션) 후,
별도 Consumer가 outbox를 읽어 Kafka에 publish한다.

> 구현 현황: 프로토타입은 Kafka 없이 DB 아웃박스 `ord_outbox_event` + `runNshop-consumer`(별도 컨슈머 앱)로 동작한다.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. 트랜잭션 내 직접 Kafka publish | 구현 단순 | DB 커밋 후 publish 실패 시 불일치 | 원자성 미보장 |
| **B. Outbox 패턴 (채택)** | DB 트랜잭션과 이벤트 원자성 보장 | outbox 테이블 관리, polling 지연 | — |
| C. CDC (Change Data Capture) | 코드 변경 최소 | 인프라 복잡도(Debezium 등), 운영 부담 | 프로토타입 단계에 과잉 |

### 결과

- 긍정: DB 트랜잭션과 이벤트 발행의 원자성 보장
- 부정: outbox polling 주기만큼 이벤트 전달 지연 (최대 수 초)
- 주의: outbox 테이블 GC 정책 필요 (처리 완료 건 주기적 삭제)

### 참여자

- 테크리드
- 주문 파트 시니어
- 인프라 담당

## ADR-007: 비동기 접수와 아웃박스

### 상태: 승인 (Accepted, 2026-10-29) — ADR-001의 선점 시점·ADR-002를 대체

### 맥락

결제하기에서 재고 선점과 PG 승인을 모두 동기로 처리하면 요청 한 건이 외부 PG 지연·재고 경합에 묶여 응답이 늦어지고,
일부 SKU 부족·PG 무응답 같은 부분 실패를 한 트랜잭션에서 되돌리기 어렵다.

### 결정

결제하기는 **동기 접수만** 한다. 같은 트랜잭션에서 주문을 `TEMP`→`STOCK_REQUESTED`로 바꾸고 아웃박스에 `STOCK_DEDUCT_REQUESTED`를 INSERT한다(ADR-006).
컨슈머가 재고를 차감(`STOCK_DEDUCTED`)하고 `PAYMENT_REQUESTED`로 Payment에 승인을 요청하며, 가상계좌는 발급 후 `DEPOSIT_PENDING`이 된다.
일부 SKU 부족은 실패 SKU만 재시도하고, 3회 소진 시 차감분을 복원하고 `STOCK_FAILED`로 종료한다. 고객 화면은 주문 상태를 조회해 진행을 표시한다.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. 전 구간 동기(재고→결제) | 즉시 결과, 구현 단순 | PG·재고 지연이 응답에 직결, 부분 실패 보상 복잡 | 부분 실패·타임아웃 대응 곤란 |
| **B. 동기 접수 + 아웃박스 비동기 (채택)** | 접수 응답 즉시, 단계별 재시도·보상, 원자성 보장 | 최종 결과가 비동기(상태 조회 필요), 컨슈머 멱등 관리 | — |
| C. 전부 비동기(접수 응답도 이벤트) | 결합도 최소 | 접수 자체의 일관성·UX 복잡 | 접수 트랜잭션은 동기가 단순 |

### 결과

- 긍정: 접수 응답 단축, 재고·결제 실패를 단계별로 재시도·복원, 도메인 결합 완화
- 부정: 주문 상태 조회(폴링)가 필요하고 최종 결과가 늦게 확정됨, 컨슈머 멱등성·순서 보장 필요
- 주의: 아웃박스 폴링 지연(ADR-006), `STOCK_FAILED` 복원의 멱등성

### 참여자

- 테크리드
- 주문 파트 시니어
- 결제 파트 시니어

## ADR-008: 결제 확인 중(CONFIRMING)·거래 조회·실패 합산

### 상태: 승인 (Accepted, 2026-10-29) — ADR-004를 개정

### 맥락

PG 승인 요청이 3초 안에 응답하지 않으면 실제로는 승인됐을 수 있다. 즉시 재요청하면 중복 승인이 생기고,
실패로 단정하면 승인된 건을 놓친다.

### 결정

승인 응답 대기는 **3초**다. 무응답이면 재요청하지 않고 결제를 **`CONFIRMING`(결제 확인 중)** 으로 두고 **PG 거래 조회**로 확정한다(REQ-PAY-005·029).
조회 결과가 승인이면 `PAID`. 미승인이면 **실패 1회로 합산**하며, 승인 실패 응답과 무응답(조회 미승인 확정)의 누적 실패가 3회 미만이면 `PENDING`으로 복귀해 **3초 고정 간격**으로 재요청하고
(같은 행·같은 멱등키·`pay_group_no` 불변), 3회에 도달하면 `CANCELLED` + `PAYMENT_FAILED`다(최초 시도 포함 총 3회 시도). `CONFIRMING` 중 같은 주문의 재결제는 차단한다.
승인 응답 수신 중 통신 장애 건은 망취소 배치(1시간 주기·3회 재시도·이후 수작업)로 정리한다(정책서 4.6.2).

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. 무응답 즉시 재요청 | 빠른 재시도 | 중복 승인 위험 | 이중 결제 가능 |
| B. 무응답을 즉시 실패 처리 | 단순 | 승인된 건을 실패로 오판 | 정합성 훼손 |
| **C. CONFIRMING + 거래 조회 + 실패 합산 (채택)** | 중복 승인 방지, 승인 건 누락 방지, 실패 횟수 일관 | 상태 1개 추가, PG 조회 API 의존 | — |

### 결과

- 긍정: 이중 승인·누락 방지, 실패 응답과 무응답이 같은 3회 한도로 일관
- 부정: `CONFIRMING` 상태·조회 API 호출 추가, 확인 중 고객 재결제 차단 UX 필요
- 주의: 조회 멱등, 망취소 대상 기록 누락 방지, 요청 원문 미저장 원칙(ADR-005)

### 참여자

- 결제 파트 시니어
- 테크리드

## ADR-009: 취소 우선과 LATE_DEPOSIT 자동 환불

### 상태: 승인 (Accepted, 2026-10-29)

### 맥락

가상계좌는 입금 통보가 비동기로 오므로 고객 취소와 입금 통보가 경합하거나, 취소 확정 뒤에 입금이 들어올 수 있다.
이때 PAID로 되돌리면 이미 복원한 재고·취소 처리와 어긋난다.

### 결정

**취소를 우선**한다. 취소(`CANCELLED`) 확정 주문에 입금 통보가 오면 결제를 `PAID`로 바꾸지 않고 입금액을 환불 대상으로 기록해,
결제 시 저장된 환불계좌(REQ-PAY-031)로 **운영자 승인 없이 자동 환불**한다(사유 `LATE_DEPOSIT`, 기준일=입금 통보 수신일, 기한 8.1.3 3영업일, REQ-PAY-030·AC-PAY-035).
계좌 오류 지급 거절은 환불실패+계좌 재등록 안내(8.7.2), PG 오류는 1시간 간격 최대 3회 재시도 후 운영자 이관(8.8.2)이다.

### 대안 비교

| 대안 | 장점 | 단점 | 탈락 사유 |
|---|---|---|---|
| A. 입금 우선(취소 번복·PAID 전환) | 고객 의도 보존 | 재고 복원·취소 클레임과 충돌 | 정합성 위험 |
| B. 입금액을 운영자가 수작업 환불 | 통제 용이 | 지연·누락, 운영 부담 | 환불 기한 준수 어려움 |
| **C. 취소 우선 + 자동 환불 (채택)** | 상태 일관, 기한 내 환불 | 환불계좌 저장 전제(가상계좌 결제 시 필수), 자동 환불 오류 대응 필요 | — |

### 결과

- 긍정: 취소 확정 상태 불변, 환불 기한 준수, 운영 부담 감소
- 부정: 가상계좌는 환불계좌 입력이 필수(마이페이지 등록 폐기), 계좌 오류 시 재등록 절차 필요
- 주의: 입금 통보 멱등·서명 검증, 환불 사유 `LATE_DEPOSIT` 구분 집계

### 참여자

- 결제 파트 시니어
- 테크리드
- 기획자
