> UC-14/API-022는 리터럴 라벨이 아니라 DK §14([DK-세부유스케이스/order.md](../../../DK-세부유스케이스/order.md))·DL §15(위 링크)의 섹션 번호 기준 암묵적 대응이다(DK 문서 본문에는 "UC-14" 문자열이 없음 — DL은 이번에 섹션 제목에 `(API-022)`와 명시적 앵커를 추가해 직접 검색·클릭 이동이 가능해졌다). ID-섹션 매칭표는 [DQ-프로그램목록/order.md](../../../DQ-프로그램목록/order.md) §1(SCR-A-001 행)에서 확인한다.

### 설계안 참고 (상태 8종·SummaryBar 8카드)

> 최초 설계안(구현 아님). 목록 base table이 `ord_order`에서 `ord_platform_order`로 전환되면서 8종 중 `준비중`·`배송중`·`배송완료`·`구매확정`은 `PlatformOrder.status`를 그 값으로 전이시키는 로직이 없어 현재 발생할 수 없다.

```
┌전체─┐ ┌─접수─┐ ┌결제완료┐ ┌준비중┐ ┌배송중┐ ┌배송완료┐ ┌구매확정┐ ┌취소─┐   ← SummaryBar 설계안 8카드
```

- 상태 Select 설계안 허용값: 전체/접수/결제완료/준비중/배송중/배송완료/구매확정/취소 8종 — [DL-인터페이스명세/order.md](../../../DL-인터페이스명세/order.md#api-022) §15 매핑표 참조.
- **"배송중" 표시 근거(설계안)**: `ord_order.status`는 `PREPARING`에서 바로 `DELIVERED`로 전이하며 "배송중"이라는 원시 상태는 없다([DH-상태머신/order.md](../../../../S2-구조설계/DH-상태머신/order.md) §1, v6 10상태). API-022/023의 `status`는 `PREPARING` + `ord_shipment(OUTBOUND)` 운송장 등록(status=IN_TRANSIT)을 서버에서 조인해 `IN_DELIVERY`로 변환하는 "표시 상태"다 — [API-022](../../../DL-인터페이스명세/order.md#api-022)(§15).

> **현행 구현 정리 (2026-10-29 통합 — 2026-10-19/20·10-23·10-26·10-27 각주 대체)**
> - **상태 Select**: `ORDER_STATUS_LABEL` 6종 — 재고확인중(`STOCK_REQUESTED`) / 재고차감완료(`STOCK_DEDUCTED`) / 재고부족(`STOCK_FAILED`) / 입금대기(`DEPOSIT_PENDING`) / 결제완료(`PAYMENT_COMPLETED`) / 취소(`CANCELLED`). 결제하기 후 재고차감이 비동기(컨슈머)로 진행되어 접수 직후 주문은 `재고확인중`→`재고차감완료`→`입금대기`로 전이하고, 재고 부족이 확정되면 `재고부족`이 된다. FE 라벨은 `DEPOSIT_PENDING`="입금대기"다(`mockData.ts`).
> - **SummaryBar**: 4개 카드(전체 / 입금대기 / 결제완료 / 취소). 서버가 `adminStatusSummaryKeys` 3종(`OrderService.kt:147-151`)만 개별 집계하며, 나머지 상태 건은 `전체`에만 포함된다. 검색조건(키워드+기간)만 반영하고 상태 선택과 무관, 0건 카드도 `0`으로 표시, `전체`는 TEMP 제외 합계. 조회 결과가 0건이어도 SummaryBar는 그려진다(`OrderHistory.tsx`).
> - **제외**: 주문서 진입 임시주문(`TEMP`)은 목록·집계에서 제외된다(`OrderMapper.xml`).
> - **뱃지**: `data-order-status`로 스타일링하며, 신규 상태 3종은 전용 색상이 없어 기본 뱃지로 표시된다. 결제완료 행에만 강조 속성(`data-exh-live`), 취소 행에 종료 속성(`data-exh-ended`)이 붙는다.
> - **엑셀 다운로드**: 버튼은 조회 전에도 보이나 "엑셀 다운로드 기능은 준비 중입니다." alert만 표시한다(미구현).
> - **조회 방식**: 진입 시 자동 조회하지 않고 [조회] 클릭(또는 키워드 Enter)으로 `GET /api/admin/v1/orders?keyword&status&from&to&page&size`를 호출한다(페이지당 기본 10건).
> - **주문번호**: admin 목록은 플랫폼 주문번호 `PyyMMdd-NNNNN-00`(예: `P261026-00001-00`, `platformOrderNo`)을 노출한다. `ORD-` 포맷은 vendor 주문번호(`Order.orderNo`)로 목록에 노출되지 않는다. 주문일시는 응답이 `YYYY-MM-DD HH24:MI`(`OrderMapper.xml`)다.
> - **금액 열**: 목록 금액은 정책(order 3.7.4)의 **주문금액**이며 매퍼는 `po.total_order_amount AS amount`를 반환한다. 결제금액(PG 결제분 = 주문금액 − 포인트)은 목록에 표시하지 않는다([tabs/SCR-A-002-T2_payment.md](SCR-A-002/SCR-A-002-T2_payment.md) 참조).

**검색·조회 규칙**
- **검색 규칙 (2026-10-27 확정 — 설계 규칙)**: 키워드는 주문번호·상품명·주문자명 모두 부분 일치(판매자명 제외, 대소문자 무시). 검색 안내 placeholder는 "주문번호 / 상품명 / 고객명"으로 표기한다. **현행 미구현**: 매퍼(`OrderMapper.xml:13-21,38-47`)는 `po.platform_order_no`와 상품명 `ILIKE`만 검색하고 `orderer_name` 컬럼은 api·db 어디에도 없어(DL은 "컬럼 추가 필요"), 고객명을 입력하면 0건이 조용히 반환된다. 후속 과제: `orderer_name` 컬럼 추가 후 검색 대상 포함.
- **기간 기준**: 주문일시(`ordered_at`). 종료일 포함, `from` > `to`이면 "시작일이 종료일보다 늦을 수 없습니다" 안내(INVALID_DATE_RANGE).
- **페이지 크기**: 10/20/50 선택(서버 허용 1~100, 기본 10). 잘못된 값은 INVALID_PAGE/INVALID_SIZE.
