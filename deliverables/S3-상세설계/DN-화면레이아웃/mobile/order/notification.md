## 5. mobile — 알림 문자/알림톡 (NotificationMessage)

> 앱 내 화면이 아닌 **외부 채널(카카오톡/알림톡)로 발송되는 메시지** 레이아웃 정의.
> 고객이 이 메시지를 클릭하면 앱 내 특정 화면(딥링크)으로 유입된다.

### 메타블록

| 항목 | 내용 |
|---|---|
| 화면 ID | 없음 (외부 채널 — DQ 프로그램목록에 SCR 미등록) |
| 앱 | mobile (딥링크 유입) |
| 접근 권한 | 해당 회원 전용 딥링크 |
| 관련 세부UC | 해당 없음 (알림 발송은 시퀀스(DM) 컨슈머 로직에서 트리거) |
| 호출 API | 해당 없음 |

### 화면 전환

> 딥링크 클릭 → SCR-M-006 (주문/배송 조회) 또는 SCR-M-010 (클레임 목록). 유형별 상세 매핑은 아래 표.

| 이벤트 | 채널 | 메시지 요약 | 딥링크 (유입 화면) |
|---|---|---|---|
| ORDER_CONFIRMED (주문확인) | 카카오톡 | "결제가 완료되었습니다. 주문번호: #{orderNo}, 결제금액: #{paidAmount}원" | `/my/orders` (목록) |
| SHIPPING_STARTED (배송시작) | 알림톡 | "[runNshop] 상품이 발송되었습니다. 송장번호: #{trackingNo}" | `/my/orders` (목록) |
| DELIVERY_COMPLETED (배송완료) | 카카오톡 | "배송이 완료되었습니다. 구매확정 시 포인트가 적립됩니다." | `/my/orders` (목록) |
| STOCK_FAILED (재고확보실패) | 알림톡 | "[runNshop] 재고 부족으로 주문이 취소되었습니다. 주문번호: #{orderNo}" | `/my/orders` (목록) |
| PAYMENT_FAILED (결제실패) | 알림톡 | "[runNshop] 결제가 승인되지 않았습니다. 주문번호: #{orderNo}. 다른 결제수단으로 다시 주문해 주세요." | `/my/orders` (목록) |
| CLAIM_RECEIVED (클레임접수) | 카카오톡 | "클레임 접수가 완료되었습니다. 처리까지 1~2일 소요됩니다." | `/my/claims` (목록) |
| CLAIM_COMPLETED (클레임완료) | 카카오톡 | "클레임 처리가 완료되었습니다. 환불은 승인 후 3영업일 이내에 요청되며 입금 반영은 은행 기준입니다." | `/my/claims` (목록) |
| REFUND_COMPLETED (환불완료) | 카카오톡 | "환불이 완료되었습니다. #{refundAmount}원이 반환됩니다." | `/my/claims` (목록) |

> [확인 필요: 결제 실패 예시 "카드 한도 초과"는 현재 가상계좌만 진행하는 흐름과 맞지 않는다. 입금기한(12시간) 만료·미입금 취소 알림 이벤트를 추가할지는 정책서 notification.md(5.10) 대조 후 휴먼 결정]

> **시점별 안내 문구 차이 (주문 접수 완료 화면 vs 알림 메시지)**
>
> | 시점 | 화면/채널 | 안내 내용 |
> |---|---|---|
> | 주문 접수 직후 ([SCR-M-003_order-complete.md](SCR-M-003_order-complete.md) 화면) | 앱 내 | "주문이 접수되었습니다" + "재고 확인 및 결제가 진행 중입니다" |
> | 결제 성공 후 (알림톡) | 카카오톡 | "결제가 완료되었습니다" + 확정 결제금액·주문번호 |
> | 결제 성공 후 (이메일, [order-email.md](order-email.md)) | 이메일 | "주문이 완료되었습니다" + 전체 주문 상세 내역 |
> | 재고 확보 실패 (알림톡) | 알림톡 | "재고 부족으로 주문이 취소되었습니다" + 주문번호 |
> | PG 결제 실패 (알림톡) | 알림톡 | "결제가 승인되지 않았습니다" + 재주문 안내 |

### 템플릿 변수

| 변수 | 설명 | 출처 |
|---|---|---|
| `#{orderNo}` | 플랫폼 주문번호 | ord_platform_order.platform_order_no |
| `#{paidAmount}` | 확정 결제 금액 | pay_payment.amount |
| `#{trackingNo}` | 운송장번호 | ord_shipping.tracking_number |
| `#{refundAmount}` | 환불 금액 | pay_payment.amount (환불분) |
| `#{claimId}` | 클레임 ID | ord_claim.id |
| `#{productName}` | 대표 상품명 (외 N건) | ord_order_item.product_name |

> **(2026-10-23 구현 확인)**: `#{orderNo}`의 출처는 `ord_platform_order.id`(raw PK)가 아니라 `ord_platform_order.platform_order_no`(화면에 노출하는 "P"+yyMMdd+"-"+5자리+"-00" 문자열 컬럼, `PlatformOrder.kt`/`OrderService.kt.nextPlatformOrderNo()`)다 — id는 내부 식별자일 뿐 표시용 포맷 문자열이 아니다. ORDER_CONFIRMED/STOCK_FAILED/PAYMENT_FAILED 알림이 쓰는 "주문번호"는 모두 이 `platformOrderNo` 값이다(admin/mobile 공통 원칙, `.agents/tasks/order-platform-order-channel-redesign/design.md` §1).

### 딥링크 보안 규칙

| 규칙 | 설명 |
|---|---|
| URL에 사용자 ID 미포함 | 딥링크에 회원 아이디·이메일·전화번호 등 식별 정보 노출 금지 |
| 로그인 후 자동 이동 | 미로그인 상태에서 딥링크 클릭 시 → 로그인 화면 → 로그인 완료 후 원래 CTA 목적지로 자동 이동 (returnUrl 패턴) |
| 토큰 기반 인증 | URL에 인증 정보 대신 앱 내 세션/토큰으로 본인 확인 |
| 예시 | ✅ `https://runNshop.com/my/orders` → 미로그인 시 `/login?returnUrl=/my/orders` → 로그인 후 `/my/orders`로 자동 이동<br/>❌ `https://runNshop.com/my/orders?userId=mem-001` |
