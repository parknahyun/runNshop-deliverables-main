> **구현 현황 (2026-10-29)**: 주문 상세 조회(API-015)만 구현돼 있다. [구매확정]·[반품/교환]·[주문취소] 버튼은 `alert("프로토타입에서는 지원하지 않는 기능입니다.")`만 띄우고(`app/my/orders/[orderId]/page.tsx`의 `ProductActionButton`·`OrderCancelBar`), 주문 취소 바는 **결제완료(PAYMENT_COMPLETED)에서만 렌더되고 입금대기에는 취소 버튼이 없다**(설계는 입금대기·결제완료 모두 노출 — 구현 갭), [배송조회] 버튼은 없다. BE `OrderController`에는 cancel·confirm·shipping-address·claims endpoint가 없어 API-010·011·012는 호출되지 않는다. 상태 라벨은 BE `MyOrderStatusLabel`(STOCK_REQUESTED·STOCK_DEDUCTED·STOCK_FAILED·DEPOSIT_PENDING 포함, PAYMENT_PENDING·PAYMENT_FAILED 없음) 기준이며 아래 "접수/결제요청중"·"결제실패" 행은 설계안이다.

### 화면 구성

| 영역 | 데이터 소스 (API) | 표시 내용 |
|---|---|---|
| Header + 상태뱃지 | GET /api/mobile/v1/my/orders/{orderId} (API-015) | "← 주문 상세" + 현재 상태 뱃지 |
| 주문 기본 정보 | 동일 API | 주문번호(platformOrderNo), 주문일시 |
| 주문 상품 목록 | 동일 API → `orders[]` → `items[]` | 판매자별 그룹(판매자명 헤더) → 상품이미지, 상품명, 옵션, **주문수량**, 상품주문금액 (할인 안분 후, 포인트 차감 전) |
| 결제 정보 | 동일 API → `payment` | 상품금액, 할인 내역, 배송비, 주문금액(`orderAmount`), 포인트 사용(`pointUsedAmount`), 결제금액(`paymentAmount`), 결제수단(마스킹), 결제일시 |
| 배송 정보 | 동일 API → `shipping` | 수령인(마스킹), 연락처(마스킹), 주소, 배송메모, 택배사, 운송장번호, 배송상태 (**마스킹은 문서 기준 — 구현 갭, 아래 각주**) |
| 주문 이력 (Timeline) | 동일 API → `history[]` | 상태 변경 이력 (최신순), 일시 + 이벤트명 |
| 상태별 액션 버튼 | — (FE 조건부) | **전부 프로토타입 미구현(alert, [배송조회]는 버튼 없음).** **상품(아이템) 단위**: [구매확정](DELIVERED, 아이템별) → 확정 후 [리뷰 작성] 전환, [반품/교환](DELIVERED, 판매자 단위 클레임 신청 이동). **판매자 단위**: [배송조회](PREPARING + shipment(OUTBOUND).status=IN_TRANSIT, v6). 배송중에는 반품/교환 버튼이 없고 배송완료 후 10일 이내에 신청한다(2026-10-29 확정). **주문 전체 단위**: [주문취소] 버튼(입금대기(DEPOSIT_PENDING)이거나 전체 판매자가 PAYMENT_COMPLETED일 때 노출) (준비중(송장 등록 전)은 취소 버튼 없이 고객센터 안내 — 유선 요청 후 어드민이 수작업 확인 후 취소) — 하단 고정 |
| BottomNav | — | 홈/기획전/검색/MY |

> **(2026-10-19/20 구현 확인/실제 구현 반영)**: 이 상세 화면은 실제로 플랫폼주문(`ord_platform_order`) 1건 기준이다(`OrderService.kt.getMyOrderDetail()`가 `platformOrderRepository.findDetailById(id)`로 조회 후 본인 소유 검증). "주문 상품 목록" 행의 판매자별 그룹은 `buildMyOrderItemGroup()`이 만드는 `orders[]`(vendor별, 각 vendor의 `items[]` 포함) 구조와 일치한다 — §8(목록)의 "대표 1건 + 외 N건" 축약과 대비되는 "전체 펼침" 단위다.

> 주문번호 표기(2026-10-29 정리): 와이어프레임 예시는 현행 P/V 체계로 갱신돼 있다 — 화면·알림이 표시하는 주문번호는 `platformOrderNo`("P"+yyMMdd+"-"+5자리+"-00")이고, vendor 주문번호(`Order.orderNo`, "V"+yyMMdd+"-"+5자리+"-NN")는 partner 채널 전용이다.

> **구현 갭 (마스킹)**: 문서는 수령인·연락처를 마스킹(`홍*동`·`010-****-5678`)해 표시하도록 정의하지만, 현재 BE(`OrderService.kt` 주문 상세 응답)는 `receiverName`·`receiverPhone`을 가공 없이 반환한다. 원천(`OrderAddressMock`) 값이 이미 마스킹돼 있는지는 확인하지 못했다. 마스킹은 문서 기준을 유지하며 구현 누락은 갭으로 기록한다(코드 미수정). [확인 필요: 마스킹을 API 계층 규칙으로 둘지 화면 규칙으로 둘지, 실제 동작]

> **구현 차이 (결제 정보 용어)**: 응답의 `payment.cartDiscount`는 쿠폰 할인(`-totalDiscountAmount`)을 담고 있어 화면에 "장바구니 할인"으로 표기되면 의미가 어긋난다. 정책 용어(주문금액·결제금액·포인트·배송비 할인금액)와의 매핑은 [DBA order.md 3.7.5](../../../../S2-구조설계/DBA-도메인정책서/order.md) 기준으로 별도 정리가 필요하다(와이어프레임은 정책 용어 기준 설계안).

> **취소 가능 상태 (2026-10-29 확정)**: 입금대기·결제완료에서 [주문취소]를 노출한다. 입금대기 취소는 가상계좌 폐기·재고 복원이며 환불 없음. 준비중(송장 등록 전)은 시스템상 취소요청 프로세스가 없다(2026-10-29 확정). 유선 요청 → 어드민이 수작업 확인 후 취소(CS 예외취소, REQ-ORD-017)이며, 송장 등록 후 배송중은 취소 불가이며, 배송완료 후 10일 이내에 반품·교환을 신청한다. 고객 화면에는 "취소는 고객센터로 문의해주세요"를 표시한다. 정책서 5.4.1·7.3.2·부록 B의 취소요청 서술과 다르므로 정책서 정정 필요.
