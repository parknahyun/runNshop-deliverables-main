> **(2026-10-19/20 구현 확인/실제 구현 반영)**: 위 "아이템 단위 표시"는 실제로는 **플랫폼주문(`ord_platform_order`) 1건 = 1행**이다 — `OrderService.kt.getMyOrders()`가 `platformOrderRepository.findByMemberIdOrderByOrderedAtDesc(memberId)`로 조회하고, 각 행의 `productName`은 대표 상품 1건 + "외 N건"(`formatRepresentative()`, admin 목록과 동일한 포맷) 형태로 묶어서 보여준다. 상세([SCR-M-007_order-detail.md](SCR-M-007_order-detail.md))는 같은 플랫폼주문을 vendor별로 펼쳐서 보여주므로, "목록=대표 1건으로 축약된 플랫폼주문 단위, 상세=vendor별로 전부 펼친 플랫폼주문 단위"가 정확한 집계 단위 차이다. 근거: `OrderService.kt.getMyOrders()`/`buildMyOrderRow()`(줄 번호는 변동되므로 생략), `apps/runNshop-mobile/components/my/OrderListItem.tsx`.

> 주문번호 표기(2026-10-29 정리): 와이어프레임 예시는 현행 P/V 체계로 갱신돼 있다 — 화면·알림이 표시하는 주문번호는 `platformOrderNo`("P"+yyMMdd+"-"+5자리+"-00")이고, vendor 주문번호(`Order.orderNo`, "V"+yyMMdd+"-"+5자리+"-NN")는 partner 채널 전용이다.

### 클레임 상태 흐름 (배송비 결제 포함)

> **v6 갱신**: 배송 실행 구간(수거중/반송 배송중)은 더 이상 `claim.status` 값이 아니다. 공용 배송실행 엔티티 `ord_shipment`(shipment_type=PICKUP/RETURN)로 분리되었고, `claim.status`는 "고객·판매자·CS가 판단·결정하는 지점"만 표현한다. 아래 흐름에서 "수거 진행 중"·"반송 배송중"으로 화면에 보이는 문구는 `claim.status` + `shipment.status` 조인으로 계산되는 파생 표시이며, 실제 claim.status 값은 아니다(예: 화면 표시 "수거중" = claim.status(PAYMENT_PENDING 결제완료 후 또는 INSPECTING 진입 전) + shipment(PICKUP).status=IN_TRANSIT).

```
[정상 흐름]
접수(RECEIVED)
  → 배송비 결제 대기(PAYMENT_PENDING) ... [고객 귀책 시, 결제완료 후 shipment(PICKUP) 자동생성·진행]
  → 품질점검(INSPECTING) ................ [shipment(PICKUP) 배송완료 시 자동 진입(고객 귀책) 또는 판매자 귀책 시 즉시 진입, 판매자: 합격/거부 판정]
  → 수거완료(PICKED_UP) ................. [판매자: 합격 확인]
  → 환불완료(REFUNDED) .................. [어드민: 환불 처리]
  → 클레임완료(COMPLETED) ............... [배치: 자동 전환]

[품질점검 거부 (수거거부)]
  → 품질점검(INSPECTING)
  → 수거거부(PICKUP_REJECTED) ........... [판매자: 불합격 + 사유 등록]
  → 어드민 판정:
     ├─ 폐기(DISPOSED) → 클레임완료(COMPLETED)
     └─ 추가결제요청 → 반송 배송비 결제 대기(RETURN_PAYMENT_PENDING) ... [고객 결제 후 shipment(RETURN) 진행] → shipment(RETURN) 배송완료 → 클레임완료(COMPLETED)

[반려 (접수 단계)]
접수(RECEIVED) → 반려(REJECTED) ......... [어드민]

[결제 미완료]
접수(RECEIVED) → 배송비 결제 대기(PAYMENT_PENDING) → 1일 초과 → 자동취소(PAYMENT_EXPIRED)
```

### 클레임 상태별 정리

> claim.status 11상태 (v6 — PICKUP/RETURN_SHIPPING/RETURN_DELIVERED는 `ord_shipment`로 이관되어 제외). 근거: `S2-구조설계/DH-상태머신/order.md` §2.

| 상태 | 설명 | 수행 주체 |
|---|---|---|
| RECEIVED | 접수됨 | 고객 신청 |
| PAYMENT_PENDING | 수거 배송비 결제 대기 ~ 수거 진행 중 (고객 귀책, shipment(PICKUP) 병행) | 고객 → 판매자 (수거정보 입력) |
| PAYMENT_EXPIRED | 결제 1일 초과 → 자동 취소 | 배치 |
| INSPECTING | 품질점검 진행 중 (판매자 귀책 즉시 또는 shipment(PICKUP) 배송완료 후 진입) | 판매자 (합격/거부 판정) |
| PICKED_UP | 수거완료 (품질점검 합격) | 판매자 |
| PICKUP_REJECTED | 수거거부 (품질점검 불합격) | 판매자 (사유 등록) |
| REFUNDED | 환불 완료 | 어드민 |
| RETURN_PAYMENT_PENDING | 반송 배송비 결제 대기 ~ 반송 진행 중 (불합격 반송, shipment(RETURN) 병행) | 고객 → 판매자 (운송장 등록) |
| DISPOSED | 폐기 처리 | 어드민 |
| COMPLETED | 클레임 전체 완료 | 배치 (자동) |
| REJECTED | 접수 단계 반려 | 어드민 |

> 수거중/반송배송중 진행 상태의 상세(운송장·이동중·배송완료 등)는 `ord_shipment.status`(PENDING/IN_TRANSIT/DELIVERED/FAILED/CANCELLED)를 참조한다.

### 수행 주체별 액션 정리

| 주체 | 가능한 액션 |
|---|---|
| **고객** | 클레임 신청, 배송비 결제, 반송 배송비 추가결제 |
| **판매자** | 수거정보 입력, 품질점검(합격/거부), 수거완료 확인, 반송 운송장 등록 |
| **어드민** | 접수 확인, 환불처리, 반려, 폐기 결정, 추가결제 요청 |
| **배치** | 결제 만료 자동취소, 환불완료→클레임완료 자동전환 |

### 화면 전환

> 주문번호 클릭 → SCR-M-007 (주문 상세). 그 외 상태별 액션 버튼의 이동 대상은 아래 표 참조.

| 주문 상태 | 표시 버튼 | 클릭 동작 (이동 화면 / API) |
|---|---|---|
| 재고확인중 (STOCK_REQUESTED) | (액션 없음) | 현행 상태 라벨 "재고확인중" |
| 재고차감완료 (STOCK_DEDUCTED) | (액션 없음) | 현행 상태 라벨 "재고차감완료" |
| 재고부족 (STOCK_FAILED) | (액션 없음) | 현행 상태 라벨 "재고부족" (재고 확보 실패 확정) |
| 입금대기 (DEPOSIT_PENDING) | [주문취소] (**설계안·프로토타입 미구현** — 2026-10-29 허용 확정) | 취소 확인 → POST /api/mobile/v1/my/orders/{orderId}/cancel (API-010). 가상계좌 폐기·재고 복원, 환불 없음. 현행 상태 라벨 "입금대기" |
| 접수 (ORDER_RECEIVED) | (액션 없음) | 현행 상태 라벨 "주문접수" |
| 결제요청중 (PAYMENT_PENDING) | (액션 없음) | **설계안** — 현행 `MyOrderStatusLabel`에 없음 |
| 결제완료 (PAYMENT_COMPLETED) | [주문취소] (**프로토타입 미구현** — alert) | 취소 확인 → POST /api/mobile/v1/my/orders/{orderId}/cancel (API-010, 같은 화면 유지) |
| 준비중 (PREPARING, 송장 등록 전) | (취소 버튼 없음) | "출고 준비 중" 안내 + "취소는 고객센터로 문의해주세요". 고객센터가 유선 요청을 받아 어드민이 **수작업 확인 후** 취소 진행(CS 예외취소, REQ-ORD-017) |
| 배송중 (order.status=PREPARING + shipment(OUTBOUND).status=IN_TRANSIT — v6: order.status 자체는 PREPARING 유지, 화면 조인 판정) | [배송조회] (**프로토타입 미구현** — alert) | 배송조회 → 택배사 배송추적 페이지 외부 이동. 송장 등록 이후는 취소 불가이며 반품·교환 버튼도 없다. "배송완료 후 반품·교환을 신청할 수 있습니다" 안내(배송완료 후 10일 이내, SCR-M-008) |
| 배송완료 (DELIVERED) | [구매확정] [반품/교환] (**프로토타입 미구현** — alert) | 구매확정 → POST /api/mobile/v1/my/orders/{orderId}/confirm (API-011, 같은 화면 유지), 반품/교환 → SCR-M-008 (반품/교환 신청, 프로토타입 라우트 없음) 이동 (고객 귀책 선택 시 배송비 안내 문구 노출: "고객 사유로 반품/교환 시 수거 배송비가 발생하며, 품질점검 불합격 시 반송 배송비가 추가로 발생할 수 있습니다.") |
| 구매확정 (CONFIRMED) | [리뷰 작성] (프로토타입 미구현 — alert) | 리뷰 작성 화면 이동 (별도 Bolt) |
| 취소 (CANCELLED) | (액션 없음) | 취소 완료 상태 |
| 결제실패 (PAYMENT_FAILED) | [다시 주문하기] | SCR-M-001 (장바구니)로 이동 — **설계안**: 현행 `MyOrderStatusLabel`에 PAYMENT_FAILED가 없고 `OrderListItem.tsx`에 [다시 주문하기]도 없다(프로토타입 미구현) |

> **취소 가능 상태 (2026-10-29 확정)**: 고객 취소는 입금대기·결제완료에서 허용한다. 준비중(PREPARING)은 **시스템상 취소요청 프로세스를 두지 않는다**. 고객이 유선으로 요청하면 어드민에서 취소를 접수한다(CS 예외취소). 따라서 고객 화면에는 취소 버튼 대신 고객센터 안내를 표시한다. 정책서 5.4.1·7.3.2·부록 B의 "상품준비중 취소요청(판매자 승인)" 서술과 다르다 — 정책서 정정 필요.
