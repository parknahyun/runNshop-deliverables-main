> **(2026-10-19/20 구현 확인/실제 구현 반영)**: 결제수단(PaymentMethod) 영역은 "[●신용카드] [ 계좌이체 ]" 2종 고정이라는 초기 설계가 아니라, 서버 응답 `payment_methods[]`를 그대로 렌더링하는 동적 목록이다(`PaymentMethod.tsx`, `methods: {type, label}[]`를 버튼으로 매핑). 현재 mock(`mobile__POST_my_orders_sheet.json`)의 `payment_methods[]`는 `VIRTUAL_ACCOUNT`(가상계좌, 배열 첫 원소 — 기본 선택)·`CARD`(신용카드) 2종을 내려준다. 결제 요청(`POST .../pay`)의 `paymentMethodType` 허용값은 이보다 넓은 `CARD`/`EASY_PAY`/`POINT`/`VIRTUAL_ACCOUNT` 4종(`OrderService.kt.validatePayRequest()`)이지만, 이 화면이 실제로 노출하는 선택 버튼은 mock이 내려주는 2종뿐이다. **(2026-10-26 변경 — 임시주문 연결)** 주문서 화면은 장바구니 "주문하기" 클릭 시 선택 상품으로 서버에 임시주문(TEMP)을 만든 뒤 `/orders/new?sheet={order_sheet_id}`로 이동해 `GET .../orders/sheet/{id}`로 저장된 주문서를 읽어 그린다(새로고침해도 같은 주문서, `sheet` 없이 접근하면 "장바구니에서 다시 주문해주세요" 안내). 상품은 서버가 임시주문에서 필터링해 내려주므로 클라이언트의 선택 상품 필터(sessionStorage)는 폐지했다. 결제하기 요청 바디에서 `items`는 제외하고 결제 실패 화면의 "다시 결제하기"는 같은 `sheet`로 복귀한다. **(2026-10-26 변경)** 현재 가상계좌만 진행한다 — `CARD` 선택 시 화면에 "🚧 카드 결제는 작업중입니다. 가상계좌를 선택해주세요." 안내가 뜨고, 결제하기 버튼 클릭 시 alert로 막는다(`PaymentMethod.tsx`/`OrderBottomBar.tsx`, 서버도 `PAYMENT_METHOD_NOT_READY` 400으로 거절). **(2026-10-26 변경 — 쿠폰·포인트 영속화)** 쿠폰 선택/해제·포인트 입력은 변경 즉시(포인트는 400ms debounce) `PUT .../orders/sheet/{id}/discount`로 임시주문에 저장되고, 서버 검증 실패 시 alert 후 마지막 저장값으로 되돌린다. 저장 중에는 결제하기를 막고, 새로고침/재진입 시 `selected_coupon_id`/`point_used`로 선택 상태를 복원한다. 결제하기 요청 바디의 `couponId`/`pointUsed`는 서버가 무시한다(저장값 사용). 가상계좌 결제 결과는 `DEPOSIT_PENDING`(입금대기)으로 생성되고, 결제상태는 `WAITING_DEPOSIT`(PG 가상계좌 발급 수신, 입금통보 처리는 미구현)이다.
>
> **(2026-10-19/20 구현 확인/실제 구현 반영)**: 쿠폰(CouponSection) 영역은 "레이어 팝업 + 서버 조합 캐시 + 자동추천" 와이어프레임과 다르게 구현되어 있다 — 팝업이 아니라 같은 섹션 내 인라인 펼침(`expanded` 상태 토글)이고, 서버 조합 캐시 호출 없이 클라이언트에서 `estimateDiscount()`로 할인 예상액을 계산한다(백엔드 `PromotionApi.validateCoupon()`과 동일한 공식을 FE가 미리 보여주는 용도, 코드 주석 근거). 가장 유리한 조합을 자동 추천하는 로직은 없고 기본 선택값은 항상 "쿠폰 사용 안 함"이다. 결제 요청(`placeOrder`) 시점에만 서버가 선택된 쿠폰 1건을 검증한다(`PromotionApi.validateCoupon()`, 미적용 시 422 `COUPON_NOT_APPLICABLE`) — "조합별 사전 계산"이 아니라 "선택된 쿠폰 1건의 사후 검증"이다. 근거: `apps/runNshop-mobile/components/order/CouponSection.tsx`, `apps/runNshop-mobile/components/order/OrderSheetClient.tsx`, `OrderService.kt.validateCouponIfPresent()`.
>
> **[갱신됨]** "결제 요청(`placeOrder`) 시점에만 검증" 서술은 옛 구현이다. 현재는 쿠폰 선택 즉시 `PUT .../sheet/{id}/discount`로 검증·영속하고("2026-10-26 변경 — 쿠폰·포인트 영속화" 각주), `placeOrder`는 저장값을 재검증한다. 두 서술이 충돌하면 "2026-10-26 변경"과 "현행화 요약"을 우선한다. 와이어프레임의 금액 예시(상품금액 526,000원 = 정상가 합계, 상품 할인 57,000원, 장바구니 할인 3,000원, 주문금액 466,000원)는 장바구니 화면과 같은 값이며 상품 카드는 판매가×수량이다.
>
> **(2026-10-23 실제 구현 반영)**: 쿠폰(CouponSection)의 인라인 펼침 목록 각 항목과 약관(TermsAgreement) 각 항목에 "상세"/"보기" 텍스트 버튼이 추가됐다 — 이 인라인 펼침 각 쿠폰 항목에 "상세" 버튼을 추가해 "최소 상품금액 N원 이상 구매 시 X% 할인, 최대 M원까지" 식 조건 문구를 오버레이 모달(`CouponDetailModal.tsx`)로 보여준다. 약관 각 항목의 "보기" 버튼도 동일한 오버레이 모달(`TermDetailModal.tsx`)로 약관 전문(`content` 필드, 신규 추가 — DL §5 참조)을 보여준다. 둘 다 순수 Tailwind 오버레이(외부 라이브러리 없음)이고, 기존 라디오/체크박스 선택 UI는 변경 없이 유지된다 — 모달 열림 상태는 선택 상태와 완전히 분리된 로컬 state라 결제 흐름에는 영향이 없다. 근거: `.agents/tasks/mobile-order-ux-gaps/design.md` 결정 1·3.

> **(2026-10-23 실제 구현 반영 — 2026-10-26 폐기)**: 주문 상품을 장바구니 선택(sessionStorage, `product_id` 매칭)으로 클라이언트에서 필터링하던 방식은 폐지됐다. 현재는 장바구니에서 주문하기 시점에 선택 상품으로 서버가 임시주문을 만들고, 주문서는 그 임시주문에 저장된 상품만 내려받아 그대로 그린다("임시주문 연결" 각주). 결제 요청 바디에도 `items`를 보내지 않는다.

> **(2026-10-26 현행화 — 주문서 현재 구현 요약)**
> - **진입**: `/orders/new?sheet={order_sheet_id}` — `GET /api/mobile/v1/my/orders/sheet/{id}`로 저장된 주문서를 읽는다. `sheet` 없음/조회 실패 시 "주문서 정보를 불러올 수 없습니다. 장바구니에서 다시 주문해주세요." 안내.
> - **배송지**: 기본 배송지 1건 표시. [변경]은 현재 "프로토타입에서는 지원하지 않는 기능입니다." alert이며 배송지 선택 레이어 팝업은 미구현(설계안). 결제 요청에는 기본 배송지 `addressId`가 전달된다.
> - **쿠폰/포인트**: 변경 즉시 서버에 영속된다(`PUT .../sheet/{id}/discount`, "쿠폰·포인트 영속화" 각주). 금액 요약은 서버 저장값 기준이며 "상품 할인/장바구니 할인"은 0이라 행 자체가 표시되지 않는다(`PriceSummary`가 0이면 숨김). 결제금액 = 상품금액 − 쿠폰 할인 − 포인트 사용(+ 배송비).
> - **결제수단**: `VIRTUAL_ACCOUNT`(기본)/`CARD` 2종. 현재 가상계좌만 진행하며 `CARD`는 "작업중" 안내.
> - **결제하기(2026-10-26 비동기화)**: 결제하기는 PG를 동기 호출하지 않는다. 서버가 주문을 `STOCK_REQUESTED`로 접수하고 재고차감 요청을 아웃박스에 적재한 뒤 즉시 응답하면 접수 완료 화면(SCR-M-003)으로 이동한다. 이후 별도 컨슈머가 상품 API로 재고를 SKU 단위로 차감(`STOCK_DEDUCTED`)하고 성공 시 PG 요청(가상계좌 발급, `DEPOSIT_PENDING`)을 진행한다. 재고 부족 등 실패는 재시도(최대 3회) 후 `STOCK_FAILED`로 확정되며 이 화면에는 동기 오류로 나타나지 않는다(접수 이후 주문 상세 상태로 확인). 서버 검증 실패(쿠폰/포인트 재검증, 필수약관, 카드 결제 등)만 접수 실패 화면(SCR-M-004)으로 간다. 근거: DL §6, DM §4-1.
