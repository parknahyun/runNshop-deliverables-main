## 3. mobile — 주문 접수 완료 (OrderCompletePage)

> **프로세스**: "결제하기" 클릭 → 주문 접수 완료 화면 즉시 노출(재고 확보 전) → 백그라운드에서 재고 확보 → 재고 확보 성공 시 PG 결제 진행 → 결제 결과에 따라 상태 갱신 또는 실패 화면 분기

### 화면 구성

| 영역 | 데이터 소스 (API) | 표시 내용 |
|---|---|---|
| 접수 완료 아이콘 + 메시지 | — | ✅ + "주문이 접수되었습니다" |
| 주문 요약 | POST .../pay 응답(sessionStorage `runnshop:lastOrderComplete`) | 주문번호(platformOrderNo), 주문금액(`totalOrderAmount`), 결제금액(`totalPayment` = 주문금액 − 포인트), 결제수단, 접수일시 |
| 배송지 정보 | 동일 응답 또는 주문서 데이터 | 수령인(마스킹 — 문서 기준, 구현 갭은 아래 각주), 주소 |
| 가상계좌 입금 안내 | 결제 요청 응답(설계안) | **[TBD-UX] 현재 화면에 영역 없음**(DQ #18 미구현). 설계안: 입금 은행·계좌번호·**입금기한**을 표시한다. 입금기한은 12시간([DBA payment.md 4.4.1](../../../../S2-구조설계/DBA-도메인정책서/payment.md))이며, 기한 내 미입금 시 처리(주문 취소 전환 등)는 정책서 기준으로 확정 후 반영한다 |
| 진행 상태 안내 | — | "⏳ 재고 확인 및 결제가 진행 중입니다. 잠시만 기다려 주세요." 고정 안내문(스피너·상태 폴링 없음). 실제 처리는 서버 컨슈머가 재고 차감 → PG 요청 순으로 비동기 진행 |
| 알림 안내 | — | "결제가 완료되면 카카오톡으로 주문 확인 안내가 발송됩니다" — **알림 발송은 미구현**(Bolt14 SC39-5 알림 템플릿·입금 통보 이후). 현재 화면은 이 문구를 그대로 노출하므로, 알림이 구현되기 전까지 문구 유지 여부는 휴먼 결정 필요(F13) |
| CTA 버튼 | — | "주문 상세 보기" → `/my/orders/{platformOrderId}`, "쇼핑 계속하기" → / |
| BottomNav | — | 홈/기획전/검색/MY |

> **구현 갭 (마스킹)**: 이 화면은 문서 기준으로 수령인을 마스킹(`홍*동`)해 표시해야 하나, 현재 구현은 `address.recipient`를 가공 없이 그대로 표시한다. 마스킹은 문서 기준을 유지하며 구현 누락은 갭으로 기록한다(코드 미수정). 마스킹이 API 계층 규칙인지 화면 규칙인지는 [확인 필요: 마스킹 적용 계층].

> | 알림 문자/알림톡 ([notification.md](notification.md)) | 재고 확보 + PG 결제 완료 후 발송 | "결제가 완료되었습니다" | 확정 결제금액·승인번호·결제일시 |
> | 주문 확인 이메일 ([order-email.md](order-email.md)) | 재고 확보 + PG 결제 완료 후 발송 | "주문이 완료되었습니다" | 확정 결제금액·결제수단·상세 내역 |

> 주문번호 표기(2026-10-29 정리): 와이어프레임 예시는 현행 P/V 체계로 갱신돼 있다 — 화면·알림이 표시하는 주문번호는 `platformOrderNo`("P"+yyMMdd+"-"+5자리+"-00")이고, vendor 주문번호(`Order.orderNo`, "V"+yyMMdd+"-"+5자리+"-NN")는 partner 채널 전용이다.

| PG 결제 실패 | 미구현(Mock PG는 항상 성공) — 설계안: 주문 접수 실패 화면([SCR-M-004_order-failed.md](SCR-M-004_order-failed.md))으로 분기 또는 알림 발송 |
